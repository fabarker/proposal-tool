Sleeve Editions

Letting the desk say exactly which resolved strategic portfolios a sleeve's products and weights apply to, so “SMA” can mean one thing for every GBP mandate and another for EUR Moderate and GBP Full, while a PWA still just picks “SMA”.

Status proposal, nothing built, nothing committed Written against commit ce6329f on datasource-dev Revised 10 September 2026, after the applicability requirement was widened

What changed since the first draft, and why the recommendation moved

The first draft recommended scoping a sleeve by currency alone, resolved by a two-level rule, and argued that risk level and allocation type were out of reach because they vary per column. The requirement is now that the desk can say, for any sleeve, which resolved strategic portfolios it applies to, in any combination: all GBP, all GBP ex-Alts, EUR Moderate together with GBP Full. That changes three things.

  • The recommendation moves from single-value scopes to applicability rules. A scope column that holds one currency cannot say “EUR Moderate or GBP Full”. An edition now carries a set of rules, each a combination over the five fields of a resolved portfolio, and applies wherever any rule matches.
  • The per-column objection was overstated, and is withdrawn. Step 2 implements the base column only; comparison columns are never implemented. A sleeve is therefore resolved against one portfolio, the base, and a rule on its risk level or allocation type is perfectly coherent. What a base change does is re-resolve, which the tool already does for a type change.
  • The universe is finite, and that is the whole design. There are 172 strategic portfolios, 688 once hedging is counted, and the tool already holds every one of them. So applicability is not evaluated as an abstract rule; it is materialised into the exact set of portfolios it names, which is what lets the console show the desk “this edition applies to 43 portfolios” and refuse an overlap before it is saved.
Recommendation

Editions with explicit applicability, materialised against the universe

A sleeve keeps its name, and the name is all a PWA sees. Behind it the desk maintains one or more editions, each holding its own products and weights and a set of rules saying which resolved strategic portfolios it applies to. The tool resolves the base portfolio against those rules, serves the one edition that applies, badges it, and pins it into the proposal record.

  1. A rule is a combination over five fields: currency, hedging, risk level, allocation type, real-assets exclusion. Blank means any; a field may list several values. An edition has one or more rules and applies where any of them matches.
  2. One optional fallback per name, with no rules, applies wherever no other edition of that name does. Everything delivered today becomes a fallback on migration.
  3. Overlap between scoped editions of one name is refused at save. The console computes each edition's portfolios and names the clash, so the desk fixes it by narrowing a rule, not by reasoning about precedence.
  4. The PWA's model is untouched. The rail lists names; the scenario stores {category → name}. A quiet badge says which edition applied. Changing the base portfolio re-resolves, and a name with no edition for the new portfolio is dropped and named, exactly as a type change does now.
  5. Delivered as two CSVs: the existing sleeves.csv plus an Edition column, and a new sleeveRules.csv, one row per rule. Today's 260 rows load unchanged.
  6. About five to six days, the console's rule builder being most of it, plus five decisions from PMG at the end.

How a sleeve works today

A sleeve is identified by its implementation type, its category and its name, unique among live sleeves, and holds products whose weights sum to one. The allocation touches it in one place, and it is a multiplication:

item['exactPct'] = catWeight * float(product['weight'])

The lookup, listSleeves(category, variant), takes neither the basis nor the portfolio key. The port seam in front of it, list_sleeves(category, basis, variant), has always received the basis and discarded it. The page already sends currency and hedging on every sleeve request and clears its sleeve cache when the basis changes. So the plumbing for “the library differs by portfolio” is largely in place; what is missing is the library's own ability to say so.

The thing a sleeve would be resolved against

A resolved strategic portfolio is five fields, all of which the tool already holds for the base column:

currencyhedgingriskLevelallocationTypeexcludeRealAssets

The first two are the scenario basis, fixed across every column. The last three are the base column's key. An all-equity book has no allocation type and no exclusion; both read NA. The universe holds 172 keys, or 688 resolved portfolios once the four hedging policies are counted, which is also the bake's count. Every rule in this document is judged against that set and nothing else.

Why the base column is enough. A scenario may carry up to four columns, but only the first is implemented: step 2's heading reads Implementing USD Moderate Full and the Implementation sheet is that portfolio's. The others are comparisons on the portfolios sheet. So a sleeve is chosen once per category, resolved once against the base, and a rule on risk level or allocation type has exactly one portfolio to be true or false of.

The approaches

The original eight, with the recommendation now a ninth that supersedes the third. Each is judged on the same questions: does the rail offer only what applies, can a PWA pick the wrong one, can weights differ, can the desk express “EUR Moderate or GBP Full”, what does the export pin, and what changes.

A

Naming convention

not viable

Encode the applicability in the name: “SMA (GBP ex-Alts)”. Nothing to build; the PWA reads the label.

For

  • Nothing to build.

Against

  • The rail offers every edition under every portfolio; nothing stops a wrong pick and the export cannot check it.
  • “EUR Moderate or GBP Full” does not fit in a name anyone would read.

Verdict. What happens if nothing is decided. Moves the burden to the PWA at the moment the tool exists to remove it.

B

Multiply the implementation types

not viable

Treat (type × currency × …) as the implementation type, reusing the mechanism that already gives one name different contents per book.

For

  • Zero schema change.

Against

  • With five fields the count of “types” is in the hundreds; the type selector becomes a restatement of choices already made.
  • Cannot express an OR across portfolios at all.

Verdict. Worse under the widened requirement than under the first.

C

Single-value scopes on the sleeve

superseded

The first draft's recommendation: one scope column per field, each holding one value or blank, resolved by specificity.

For

  • Simplest possible schema; the PWA model is unchanged.

Against

  • One value per field cannot say “GBP or EUR”, and one row cannot say “EUR Moderate or GBP Full”. The desk would duplicate a product list across rows to express an OR, and maintain the copies by hand.
  • Nested scopes, such as “all GBP” and “GBP ex-Alts”, force a precedence rule.

Verdict. Right for the original ask, insufficient for this one. It survives inside I as the shape of a single rule.

D

Precedence: most specific edition wins

alternative policy

Allow editions of one name to overlap and resolve by counting constrained fields: “GBP ex-Alts” beats “all GBP”. Ties are refused at save.

For

  • Lets the desk write the natural pair, a broad edition and a narrow override, without carving the override out of the broad rule.

Against

  • “Which edition did I get, and why” needs explaining on the rail and in the workbook every time an override fires.
  • Ties are real: in this universe “GBP ex-Alts” and “GBP Moderate” share one portfolio and neither is more specific. The save-time check is needed anyway.

Verdict. Not an alternative model but an alternative conflict policy for I, and one of the decisions at the end. Recommended against, narrowly.

E

Rule-based sleeves resolved from product attributes

not now

A sleeve holds roles, filled at run time from the catalogue by exposure currency, vehicle and asset class.

For

  • One definition serves every portfolio.

Against

  • Weights cannot differ by portfolio, and the requirement is that they do.
  • The desk loses “this fund, at this weight”; the register pins something the catalogue can later contradict.

Verdict. A screener, not a library. Right only if PMG wants sleeves to follow the catalogue automatically.

F

Product substitution map

partial

Sleeves stay portfolio-blind; a map swaps a product for its local equivalent. Weights untouched.

Verdict. Cannot vary weights or product count, so fails the stated case. Could later complement I for share-class and listing differences.

G

Per-scenario sleeve editing

not viable

Let the PWA adjust products and weights inside a scenario.

Verdict. Undoes the library the two-tier entitlement was built to protect; nothing is learned across proposals. Listed to be rejected.

H

Hedging as a share-class choice

adjacent

Where hedging changes only the share class of the same fund at the same weight, that belongs on the product. Where it changes the composition, hedging is a rule field in I and the desk writes an edition for it. Both can coexist.

Verdict. No longer a reason to keep hedging out of the sleeve; it is a reason to keep the product-level path open too.

I

Editions with explicit applicability rules, materialised

recommended

A sleeve name has one or more editions. Each edition holds products and weights and a set of rules; a rule constrains any of the five fields, with any-of lists per field; an edition applies to a portfolio when any rule matches. One edition per name may have no rules and is the fallback. The tool expands every edition's rules into the exact set of portfolios in the universe, uses that set to resolve the base portfolio, and uses the same sets to refuse overlap between scoped editions of a name at save.

For

  • Expresses every example given, and any other combination, as data the desk can read back.
  • The PWA sees one name per sleeve; the wrong pick is impossible because only the applicable edition is served.
  • Materialisation makes applicability visible and overlap detectable before it is saved, because the universe is finite and already loaded.
  • Each edition is its own row with its own history, revert and archive; the register pins exactly what was proposed.
  • The page needs one badge; the seam already carries the basis; the base key is already in hand.

Against

  • A second table and a rule builder in the console, which is real work.
  • A rule expressed by exclusion (“all GBP except ex-Alts”) has to be written by listing what remains, unless the precedence policy is adopted instead.
  • Two delivery files rather than one.

Verdict. The smallest model that meets the widened requirement without asking a PWA to think about it. Detailed below.

The recommendation in detail

The model

  • A sleeve option is what the PWA sees: a name, under a type and a category.
  • An edition is a library row: the option's name, a short edition label (“GBP”, “EUR Moderate / GBP Full”), products and weights, and zero or more rules. The label is what the rail badges and the workbook prints; it is the desk's words, not the rule spelled out.
  • A rule constrains any subset of the five fields. A constrained field lists one or more allowed values. An unconstrained field means any. A rule matches a portfolio when every constrained field contains the portfolio's value.
  • An edition's applicability is the set of portfolios in the universe matched by any of its rules. An edition with no rules is the name's fallback; at most one per name.

Resolution, given the base portfolio

Firstan edition whose rules matchExactly one can, because scoped editions of a name may not overlap.Served, and badged with its label.
Otherwisethe fallbackThe edition with no rules, if the name has one.What every sleeve delivered today becomes on migration.
Neithernot offeredThe name does not appear under this portfolio.Not an error; the same state as a category with no sleeve under a type.

Conflict policy

Two scoped editions of the same name whose applicability sets intersect are refused at save, and the console names the portfolios they share. The desk resolves it by narrowing one rule. This is the refuse overlap policy; the alternative, most specific wins (D), is decision 2 below. The refusal is possible only because applicability is materialised: the check is a set intersection over at most 688 items, not a reasoning problem.

What using it looks like

The desk, in the repository console

  1. Open the library and pick a category. Sleeves are listed by name; a name with more than one edition shows them grouped beneath it, each with its label and its portfolio count.List: “SMA · fallback · 3 products” / “GBP · 36 portfolios” / “GBP ex-Alts · 7 portfolios”.
  2. Add an edition from an existing one. The new edition opens pre-filled with that edition's products and weights, so the desk edits rather than retypes.Editor footer: Add edition, beside Create sleeve.
  3. Give it a label. Short, in the desk's words. This is what the rail badges.Field: Edition label, e.g. “GBP ex-Alts”.
  4. Build the rules. Five rows of checkboxes, one per field, nothing ticked meaning any. Tick GBP under currency and ex-Alts under allocation type. Add another rule starts a second row for an OR.Rule builder, with the live line “applies to 7 of 172 portfolios · 28 resolved”, and a show link that lists them.
  5. See the clash before saving. If another edition of the same name shares any portfolio, the builder shows the count in red and lists the keys. Save is disabled until a rule is narrowed.“Overlaps GBP on 7 portfolios: GBP|LowVol|ex-Alts|0, …”
  6. Set the products and weights as today. The same checks run: weights to one, fee groups priced, minimums present.
  7. Save. A revision is written for that edition; history, revert, archive and restore are per edition, unchanged from how they work for a sleeve now.
  8. Optionally, import. A delivered sleeves.csv and sleeveRules.csv seed the library on first open, with the same overlap check refusing a bad delivery whole and naming the rows.

The PWA, in the tool

  1. Start a proposal, set the basis, choose the type and the base portfolio. Unchanged.
  2. Step 2: pick a sleeve per category. The rail lists names, once each, exactly as now. “SMA” is one line.
  3. See which edition applied. The chosen-sleeve pill carries a small badge with the edition's label when the edition is not the fallback. Nothing to choose; it is information.“SMA GBP ex-Alts”
  4. Change the base portfolio or the basis, and every chosen sleeve is re-resolved. A name with no edition for the new portfolio is dropped and the rail says so, the same notice a type change gives today; the PWA re-picks. There is never a silent substitution.
  5. Export. The gate requires every category to have a sleeve that resolves under the base portfolio. The workbook's Implementation preamble names the edition; the rows print the products it holds.

Data delivery, on the Cyrus side

  1. sleeves.csv gains one column, Edition, the label. Blank means the fallback. Today's 260 rows have it blank and load as fallbacks.Variant, Category, Sleeve, Edition, ProductId, Weight
  2. sleeveRules.csv is new: one row per rule. Blank cell means any; several values in a cell are separated by |. Several rows for one edition are an OR.
  3. The template workbook gains the sheet, and Appendix C of the porting guide documents both.

Why rules are stored as data, not as a string

Because the tool has to evaluate them, count them, intersect them and print them, and the console has to build them with checkboxes. A grammar in a string would need a parser, an error vocabulary and an editor; five columns and a | need none of those, and the CSV reads as a table.

Why applicability is materialised rather than evaluated

Evaluating a rule against one portfolio is trivial either way. Materialising it into a set is what makes the console honest: the desk sees a count and a list rather than a promise, overlap becomes an intersection the tool can name, and an unknown value is caught at save rather than at the moment a PWA picks. It costs nothing at 688 items and is recomputed only when the universe reloads.

What this deliberately does not do

  • No precedence by default. Exactly one edition can apply, so “which one did I get” has one answer with no reasoning. Decision 2 can reverse this.
  • No per-column sleeves. Comparison columns are never implemented, so they carry no sleeves. If a future version implements more than one column, each would be resolved separately by the same rules, and nothing here prevents that.
  • No mandate-size rules. Eligibility by size is already handled per product through minimums and the export gate; folding it into rules would create two mechanisms for one question.
  • No PWA-side choice between editions. The label is shown after the fact. A PWA who wants the other edition wants a different portfolio, and should change that.

  2. Refuse overlap, or most specific wins? Refusal means a broad edition must carve out its narrow sibling by listing what remains, which the console helps with.
