Proposal tool · implementation plan · no code changed

A PowerPoint beside the workbook

A plan for a Download PowerPoint button at the end of the proposal flow: one slide per sheet of the Excel export, the same tables in the same styling, driven by the same engine — so a styling change made once appears in both files.

Grounded in scenario/workbook.py (the writer the brief attaches as w.txt), the export route in dashboardRouter.py, and the golden workbook the suite compares against. Every figure in the slide mock-ups below is real, read from the golden payloads and the baked estimates.

Revised 25 Sep: section 10 examines the independent plan in powerpoint-export-plan-original.html — where the two agree, where they genuinely part, which is stronger under which reading of “exactly the same”, and the seven of its points now folded into this plan (marked A1–A7 where they land).

03 · The blocker, preciselyWhere styling is welded to openpyxl

Five distinct kinds of coupling, each with its exact remedy. Everything else in the writer can be shared as-is.

#CouplingWhere it showsWhat has to change
C1Style objects are openpyxl classes, built at write time. Font('Aptos Narrow', 12, bold, 'FFFFFF'), PatternFill('solid', _HEADER_NAVY), Border(top=_DOTTED), Alignment(horizontal='right', indent=4).Every write*Sheet; e.g. the font block at the top of writeImplementationSheet, the style()/paint() closures.Styles become plain data — face, size, bold, hex ink, hex fill, border kind (hair/dotted/thin/thick + colour), alignment, indent — declared once in the builder; each renderer maps them mechanically to its own classes.
C2Layout decisions and cell painting happen in the same loop. The builders append to sheet and style sheet.cell(row, col) as they go; there is no intermediate structure a second format could read.writePortfoliosSheet's style(), writeRiskDashboardSheet's paint()/merge(), the group/item/total loops of the implementation sheet.Split each into build*Doc(payloads) → SheetDoc (all decisions, no I/O) and renderers that only transcribe. The split is a refactor of statement order, not of logic.
C3Number formats are Excel display strings. '0.00%' '0.0%' '0%' '0.0' '0.00' '$#,##0' 'mmm-yy' 'General' — Excel renders them at view time; a PowerPoint table cell holds text and renders nothing._weightCell/_feeCell/_bpCell (workbook.py:540–555), every fmt= argument, _ASSUMPTION_COLUMNS.The Doc keeps value + format string; a new renderNumber(value, fmt) renders those eight formats to text for PowerPoint. Excel keeps live values + formats, so the workbook is unchanged.
C4Conditional formatting is an Excel rule object. The stress block's red-below-zero / green-above-zero is a CellIsRule applied to a range — resolved by Excel at display time.writeRiskDashboardSheet, lines ~1002–1010.The Doc declares the rule once (SignRule(range, neg='9C0006', pos='006100')). The Excel renderer emits the same CellIsRule (golden files stay identical); the PowerPoint renderer resolves it per cell from the value's sign.
C5Charts read from worksheet cells. An Excel chart must reference a range, so slices live on the hidden chartData sheet; PowerPoint charts take data directly.writeDonutCharts (workbook.py:379).donutBreakdown() already returns the slices with palette slots. A DonutSpec (title, slices, hole 55%, size) joins the Doc; the Excel renderer keeps the hidden-sheet mechanics, the PowerPoint renderer feeds CategoryChartData and colours points from the same slots.

Deliberately not shared: protectSheet, freeze panes, print titles, tab colour and the marginal-schedule preamble mechanics of where things sit on a canvas. Excel keeps its sheet-shaped extras; PowerPoint gets slide-shaped ones (footers, headings). Sharing them would mean inventing fake equivalents on both sides.

A small intermediate representation — the SheetDoc — sits between the existing model functions and the two file formats. It is the only place layout and styling are decided.

Why this is genuinely one source

  • A styling change is one edit. Change the band fill from D3DDEA in buildImplementationDoc and the next Excel download and the next deck both carry it — neither renderer knows a colour of its own.
  • A content change is one edit. Add a column to IMPL_COLUMNS or a metric row to the portfolios builder and both outputs grow it, because both render the same rows.
  • The renderers are dumb by construction. Each is a mechanical mapping (≈150–250 lines) with no opinions: neutral style attrs → openpyxl.styles on one side, Pt/RGBColor/PP_ALIGN + table XML on the other. Code review can hold them to "no literals" as a rule.
  • The existing guarantee gets stronger, not weaker. The golden test (compareSheets, test_scenario_backend.py:1784) already diffs every cell's value, format, font, fill, merge, row height and column width against a captured reference workbook. It runs unchanged across the refactor — if the Doc split moves a single cell or shade, the diff is the review.

Sheets → slides: the page model

A Doc marks its natural break rows (a category band, a risk section subhead, an assumptions category). paginate() cuts a Doc into slide-sized pages only at those marks, repeating the header rows — the same convention as the workbook's fitToWidth=1 + print_title_rows. Each slide scales the whole table by one factor (fonts, row heights, column widths together) to fit the 16:9 content box, so proportions — and therefore the look — are preserved exactly. Typical proposal: portfolios 1 slide, risk dashboard 1–2, implementation 1–2, composition charts 1, assumptions 1–2 → 5–8 slides, matching the workbook's 4–8 printed pages.

A2, adopted: the page plan becomes an explicit, shared contract. The original plan is right that today the workbook has no print contract — no paper size, no print areas, no manual breaks; fitToWidth=1, fitToHeight=0 leaves pagination to whatever Excel build opens the file, and the five charts anchor at columns A/E/I/M/Q with extents past the table's last column. So paginate()'s output — the page manifest — is written back into the Excel print setup too (declared paper size, row breaks at the same section marks, print areas that include chart extents). One manifest, two projections: the workbook then prints in the same pages the deck shows, and “4–8 pages” becomes a contract instead of a hope. Phase 1 captures a real export at the one/four-portfolio and fees-on/off extremes to calibrate the row budget.

A4, adopted — the sign rule's fine print: the deck's per-cell resolution evaluates the raw value, not the printed one — a −0.04% that prints as “0.0%” is still red, exactly as Excel's <0 rule behaves — and an exact zero keeps the base ink, because CellIsRule uses strict inequalities.

05 · The surfaceEndpoint, button, filename, UID

  • Save barrier first (A1, adopted from the original plan). Several setters fire PUTs nobody awaits — persistBasis() (core.js:665) and setTacticalTilt() (core.js:792) launch apiFetch with only a .catch — so an export clicked right after a toggle can snapshot the scenario mid-write. Both export buttons await pending writes before POSTing, and a failed save blocks export with its own message. This fixes a latent race the Excel button has today.
  • Route: POST /scenario/{scenarioId}/export.pptx beside the existing export. Same validation, same sleeve checks, same below-minimum refusal, and the model built once and passed down — the deck must refuse exactly where the workbook refuses. Route count 31→32; the four route-inventory tests learn it.
  • Port: build_export_deck(basis, mandate, portfolios, implementation) on ScenarioPort (scenarioPort.py:89) with the one real implementation shared by the baked, fixtures and live adapters — mirroring how all three delegate to writeWorkbook today.
  • Button: the export card (implementation.js:2288) gains Download PowerPoint as a quieter sibling of Download Excel — same exportGate, same busy/error handling; exportWorkbook() generalises to exportFile(kind) and both buttons call it.
  • Not a delivery (recommended). The register records delivered workbooks: one UID per proposal, stamped and verified (stampedProposalId, D75), refused if mismatched. The deck should neither mint a UID nor write a register row. It stamps the scenario's latest delivered UID in every slide footer and in the file's core properties when one exists — and a “Draft — no delivered proposal for this scenario” footnote when none does. Pleasing detail: stampedProposalId() reads docProps/core.xml, which a .pptx has too, so the same function verifies both file kinds unchanged.
  • Same figures as the delivered file (A3, adopted). When the deck cites a delivered UID, it is built from that proposal's recorded implemented model (proposalRegister.getProposal) rather than a fresh build — so the two files a client holds cannot disagree even if the fee card or a sleeve edition has moved since. A fresh build happens only in the Draft case, where there is nothing recorded to agree with.
  • The card's copy (A7, adopted): the export card is retitled Download the proposal with both buttons beside it, and its description finally names all four sheets — today it reads “Generates Portfolios, Risk Dashboard and Implementation sheets” and omits assumptions.
  • Filename: the exportFilename pattern with the extension swapped — PMG_Scenario_USD_Hedged_2026-09-25_pr_….pptx — via Content-Disposition, as today.
  • Dependency: python-pptx (1.0.2 already in this environment) becomes a declared service dependency alongside openpyxl.

07 · Honesty sectionRisks and limits to 1:1 parity

08 · Proof, not promiseHow parity is tested

  • The golden guard, unchanged: the existing cell-for-cell comparison against engine_USD_Hedged_2col.xlsx must stay green through the whole refactor — it is what “the Excel export did not change” means.
  • Cross-format parity test (new): build the golden case once; walk the SheetDocs; for every cell assert the workbook holds its value+format and the deck's table holds renderNumber(value, fmt), same fill, same ink, same bold — read back with openpyxl and python-pptx respectively. Machine-checked 1:1, not eyeballed.
  • renderNumber unit tests: the eight formats against known Excel renderings, including $#,##0 rounding and mmm-yy.
  • Chart tests: slices, palette slots and hole size read back from the chart XML; slice shares close on 100.0.
  • Stamp test: stampedProposalId(deckBytes) returns the same UID convention (it already reads docProps/core.xml, which .pptx shares).
  • Route tests: the four route-inventory tests learn export.pptx; gate tests assert the deck refuses exactly where the workbook refuses (missing sleeves, breaches).

10 · Second opinionThe original plan, examined

An independent plan for the same feature sits in proposals/powerpoint-export-plan-original.html. It is thorough and largely correct about the code. The two plans agree on most of the foundations and part company on exactly one load-bearing question: what a slide's table actually is.

Where the two plans independently agree

  • The same refactor. Both extract a neutral, openpyxl-free report model (its reporting/model.py + theme.py + builders.py + formats.py is this plan's sheetDoc.py by another arrangement), keep Excel-only serialisation in one adapter, keep writeWorkbook()'s signature as a compatibility wrapper, and hold the whole refactor to the existing golden diff with engineParity preserved.
  • The same coupling inventory. Line for line, it names the same five welds this plan's C1–C5 name — inline style objects, painting inside the layout loops, Excel display-time number formats (the same eight, catalogued), the CellIsRule, and charts fed from the hidden sheet. Two readings of the writer converged on the same list, which is good evidence the list is right.
  • The same seams. Reuse exportGate and exportWorkbook()'s plumbing; one export path through the port shared by all three adapters; the deck must refuse exactly where the workbook refuses; chartData must never become a slide; w.txt was absent for both of us and identified the same way.

The one real divergence

The original recommends: generate the workbook, render its print pages to images with a qualified renderer, and place those images on slides beneath native heading/footnote text. This plan recommends: native PowerPoint tables and charts driven by the same builders. Everything else each document does — its bundle registry, my lighter UID rule; its renderer worker, my border helpers — follows from that choice.

Verdict, honestly

If “exactly the same” must mean pixels, the original plan is the better plan. Its central criticism of this approach is correct and worth conceding plainly: a shared data model guarantees shared decisions, not shared rendering, and no native-table route can promise visual identity with Excel. It is also more rigorous than this plan was about two adjacent facts: that the workbook today has no real print contract (so “one slide per page” needs pages to be defined before they can be matched), and that export can race unsaved writes. Both corrections are adopted above (A1, A2).

If “exactly the same” means what a reader and a reviewer would check — the same figures, formats, fonts, fills, rules and proportions, in a deck that behaves like a deck — then native tables deliver it at a fraction of the cost, with no licence, no worker fleet, and text a client can select, search and (deliberately) edit. A deck of screenshots satisfies the letter of 1:1 and loses part of the point of asking for PowerPoint.

So the parity bar becomes Decision 1 below, and the two plans compose rather than compete: the shared-model refactor is common to both routes and is where the work starts either way; the page manifest (A2) is exactly what the image route would also need; and if the bar is later raised to pixels, the original's renderer spike bolts onto this plan's phase 3 without unwinding anything.

Declined, with reasons

  • The bundle identity, revision tokens and proposalArtifacts table as v1. 11 · Yours to callOpen decisions

  • Decision 1 — what does “exactly the same” mean? Same styling decisions, figures and proportions in native, editable tables (this plan's default) — or pixel-identical images of the rendered workbook (the original plan's route, with its renderer qualification and licensing)? Everything in section 10 turns on this one answer; the shared refactor is common to both, so no work is wasted while you decide.
  • Does the deck mint or record anything? Recommended: no — it stamps the latest delivered UID when one exists, and carries a Draft footnote otherwise. Alternatives: refuse to build a deck until the workbook has been exported (strictest), or record decks in the register alongside workbooks (heaviest; new invariants).
  • A cover slide? The workbook has no equivalent sheet, so slide 1 breaks strict one-slide-per-sheet. Recommended: keep it — a deck opening on a dense table is odd — but it is one flag to drop.
  • Slide order. Recommended narrative order: allocation → risk → implementation → composition → assumptions. The workbook's own sheet order (portfolios, risk_dashboard, assumptions, Implementation) is the alternative if the deck should mirror the file exactly.
  • Where the composition charts sit. On the sheet they hang under the implementation table; on a slide they deserve their own. Recommended: own slide, headed by the caption the sheet already writes.
