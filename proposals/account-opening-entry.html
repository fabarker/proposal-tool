Proposal · Account opening

Where account opening begins

Today the account opening request is a third button inside the Start a proposal card — a card whose entire subject is beginning something that the account request requires to have already finished. Seven options for putting the entry where the work actually is, with one recommendation.

“…this sits in a start proposal card, which makes no sense because opening account is in some ways independent to starting a proposal scenario, in fact it IMPLIES that has already been done, since the account opening request requires a proposal uid.”

01The complaint, stated exactly

The path a PWA walks today to raise an account opening request, and where it goes wrong.

Step 1Land on the home page
Step 2 · wrongPress Start Here — the control for beginning a proposal
Step 3 · wrongInside the Start a proposal card, ignore the mandate fields and press the third button
Step 4 · wrongType a 12–hex Proposal UID the tool never showed you
Step 5Fill nine fields and submit

Three of the five steps are wrong, and they are wrong in different ways. Step 2 asks the user to declare they are starting a proposal when they are not. Step 3 buries a terminal action among the controls of an opening one. Step 4 asks for a fact the user can only get by going to their downloads folder and reading a filename.

02What the code does today

Six facts, each read off the source rather than assumed. They decide which options are cheap and which are not.

One door, and it is the wrong one

id="dlgaccount" is emitted only in the first branch — the landing variant of the card. Edit mandate does not carry it; no step, rail or menu carries it. Miss that button and the feature does not exist.

core.js · renderDialog()
Opening it destroys work

if (draft) { draft = null; renderDialog(); } — the mandate draft is discarded with no warning. A mis-click costs the three fields the user just filled.

core.js · openAccountDialog()
The tool already knows the UID — and drops it

The export response carries X-Proposal-Id, and the UID sits inside the filename the page already parses into a local variable. Both are discarded; the page announces “Workbook downloaded.” and nothing more.

dashboardRouter.py · implementation.js · exportWorkbook()
The 404 sends you to a filename

A UID that does not resolve returns: “Check the end of the workbook's name or cell B1 of its Implementation sheet.” That is the product telling the user to go and read a spreadsheet to operate the product.

dashboardRouter.py · lookupProposal()
A PWA cannot list their own proposals

GET /scenario/repository/proposals — the register — is requireAdmin. There is no caller-scoped list. This is the structural reason the UID must be typed at all.

dashboardRouter.py
One request per proposal — invisibly

A second request is refused naming the first (D76). But nothing in the UI — not even the admin console — shows which proposals already have a request, so the refusal only ever arrives as a surprise at submit time.

accountRequests.py · repository.js (no account view)
Worth fixing while we are here

GET /scenario/proposals/{proposalId} and GET /scenario/account-requests/{requestId} carry no auth dependency at all. Today the UID is effectively the only secret protecting a proposal's client name, mandate size and sleeve list — and that UID is printed in a filename that travels by email. Any option below that touches this route should put requireAuth on it.

One scenario mints many proposals

proposalRegister.newProposalId() runs on every export, so a scenario exported three times has produced three distinct proposals, each with its own UID and register row. The unit the account request attaches to is the proposal, not the scenario. This rules out one otherwise-tempting option (see 6) and shapes what the picker in option 3 must list.

03Diagnosis: three faults, not one

Moving the button fixes one of them. It is worth being clear which.

Fault A · Placement

A terminal action sits among the controls of an opening one, where its only available neighbours are Continue and Cancel. This is the fault you named.

Fault B · Timing

The action is offered at the one moment it can never be used — before any proposal exists — and withheld at the one moment it always can: the second after an export mints a UID.

Fault C · Identity

The UID is a handle the system owns and the user does not. Asking for it as free text makes the user the courier of the system's own primary key.

Fault B is the cheapest to fix and probably removes most of the pain on its own: a PWA who has just exported never has to find a UID again. Fault C is what makes the flow survivable weeks later, when the proposal has gone to the client and the request comes back. Fault A is a five-minute move once B and C give the action somewhere honest to live.

04What a fix has to satisfy

Constraints the options are scored against, drawn from the model rather than from taste.

  1. It must work cold.A request may be raised weeks after delivery, in a fresh session, with no scenario loaded. Any design that only works inside a live scenario fails the main case.
  2. It must work warm.The commonest case is almost certainly “I just exported and I want the account opened.” That path should require no UID at all.
  3. It must not claim a proposal exists when it does not.The entry must read as an action on delivered work, never as an alternative way to start.
  4. One per proposal must be visible before submit.The D76 refusal should be surfaced as state, not delivered as an error after nine fields.
  5. It must stay usable by a PWA.Admin-only is not a solution; the person raising the request is the advisor, not the console operator.

05Option 1 · Hand over the UID at the moment it is minted

01

The export completes into a handover panel

SmallRecommendedFront end only

A successful export currently ends in a six-word announcement. Instead, the export button's place is taken by a completion panel that states the Proposal UID, offers to copy it, and offers the account opening request as the obvious next action — opening the form with the UID already resolved, skipping the lookup entirely.

What it gains

  • Fixes fault B outright, for what is likely the majority path.
  • The UID stops being a secret the user has to go and find.
  • Gives the export an ending. Today it just stops.
  • Nothing to type, so nothing to mistype: the 422/404 branches never fire on this path.

What it costs

  • Does nothing for the cold case — a request raised next month still needs a route.
  • The account dialog is defined in core.js and opened from the landing card; it needs a way in from step 2.
  • One more state in the export gate to design and test.
Build Read resp.headers.get('X-Proposal-Id') in exportWorkbook() (the value is already on the wire), store it on App.exporting(), and render the panel in place of the export control. Expose openAccountDialog(uid) so a supplied UID lands in account.uid and goes straight to status:'looking'. No backend change whatsoever.

07Option 3 · Pick a proposal, don't type its key

03

Your delivered proposals, as a list

MediumRecommendedBackend change

The reason the flow demands a UID is that the register is admin-only, so the advisor has no way to see their own work. Add a caller-scoped list — GET /scenario/proposals/mine — and the first screen of the account flow becomes a short list of proposals you delivered, each showing whether a request already exists. Typing a UID survives as the fallback for a proposal that is not yours.

  • Surfaces the one-per-proposal rule before the form, as a badge rather than a submit-time refusal (requirement 4).

10Option 6 · Make it a fourth step

06

Step 4 · Account opening, inside the scenario

LargeNot recommended

Extend the stepper: asset allocation, implementation, then account opening, unlocked once an export has happened. Superficially the tidiest story — one continuous workflow from mandate to open account.

Step 1Asset allocation
Step 2Implementation
Step 3 · doesn't fitAccount opening

What it gains

  • One legible narrative, with the request where the work ends.
  • Reuses the stepper, the rail and the gate pattern already built.

What it costs

  • Fails requirement 1. The commonest real case is a request raised long after the scenario was last opened.
  • A scenario is not a proposal: each export mints a new UID, so “the” proposal of a scenario is ambiguous by construction.
  • The request is one-per-proposal and permanent; a scenario is a working document that keeps changing under it.
  • Makes the step-3 state depend on register history, which the scenario store does not hold.

Verdict: the attraction is real but the model does not support it. Option 1 delivers the same “the work continues” feeling without pretending the request belongs to the scenario.

13Recommendation

Options 1, 2 and 3, in that order — they attack the three faults one each, and each is useful on the day it ships.

  1. Ship option 1 first.It is the cheapest thing here, needs no backend work at all, and almost certainly removes most of the pain: the advisor who has just exported is handed the UID and a button, and never goes looking for either. The value is already on the wire — today the page reads the header's neighbour and throws this one away.
  2. Then option 2, absorbing option 7.Move the action out of the Start a proposal card and onto the landing page as a named second door. This is the literal answer to the complaint, and it retires the draft-destroying line at the top of openAccountDialog(). If the second door feels heavy on a landing page you like as it is, fall back to option 7's foot-of-card treatment — but the door is better.
  3. Then option 3, with the auth fix.The caller-scoped list is the only thing that makes the cold path pleasant, and it is the change that lets the one-per-proposal rule show up as a badge instead of an error. Take requireAuth on lookupProposal and account-requests/{id} in the same commit — adding a picker while a UID in a filename remains the only protection would be the wrong order.
  4. Take option 5 as a rider on 1 and 3.Once the picker exists and the lookup requires auth, the deep link costs an hour and makes hand-off work by mail.
  5. Take option 4 when the console next gets attention.It reuses option 3's join and fixes a real gap — an admin cannot currently see a single account request — but it is not on the critical path for the complaint.
After all three

The warm path is: export → Start account opening request → nine fields → done. No UID, no landing page, no card.

The cold path is: land → Open an account → pick the proposal from your list → nine fields → done. Still no UID.

The UID field survives for the case it was actually right for all along: a proposal that is not yours, handed to you by someone who has it.

14Decisions I need

  • Whose proposals go in the list? The register row carries exportedBy, createdBy and primaryPwa, and they are not always the same person. My instinct is primaryPwa OR exportedBy — the advisor the mandate names, plus whoever actually produced the file — so cover works without a team model. Say if it should be narrower.
  • Should the second door be visible to everyone? A user who has never exported anything would open it onto an empty list. Showing it always is honest and teaches the feature exists; hiding it until the register has a row for you is tidier. I would show it always, with an empty state that explains the precondition.
  • Does a re-export supersede the earlier proposal? Today three exports leave three live rows and a request may be raised against any of them. The picker will make that visible for the first time, and it may not be what you want. If later exports should retire earlier ones, that is a register rule, not a UI one — the mock in option 3 shows a Superseded badge on the assumption you might want it.
  • May someone raise a request against a proposal they did not write? Option 4 assumes yes for admins. If Onboarding requires the raiser to be the proposal's advisor, the UID fallback needs a matching check on POST /scenario/account-requests, which it does not have today.
  • Where does a submitted request live afterwards? The receipt is shown once and then gone — there is no way back to a request except by knowing its id, and no screen lists them. Worth deciding now whether the picker's badge should link through to the request.
