FirstMost of this already works

Before designing anything: I loaded proposalTool.html#repository with no scenario in the URL, signed in as an admin. The console opened, fully working — sleeves, editor, history, all five views. Closing it returned to the landing page. So this is not a plumbing problem.

Already true

The console has no scenario dependency. /scenario/repository is a flat endpoint, and the schema — which carries capabilities.canAdmin — is fetched on boot whether or not a scenario is asked for.

Already true

All five views deep-link: #repository, #catalogue, #archive, #activity, #proposals, each restoring its own filters. An admin could bookmark one today.

Already true

Closing from a cold page lands on the landing page, and the hash is cleared. The return path is already coherent.

Missing

The only visible entry is the rail’s admin bar — and body.phase-landing .rail{display:none}. On the landing page the bar exists in the DOM and cannot be seen.

Missing

Nothing on the landing page mentions the library at all. An admin has to know a URL fragment, or start a scenario they do not want in order to reveal the rail.

Degrades

The catalogue prices against the open mandate. Cold it reads unpriced — no mandate open, Mgmt is a dash and All-in equals product cost. Honest, but see the cold-catalogue question.

So the work is one decision, not a project: where on the landing page does the way in live, and what does it look like? Every option below is a front door onto machinery that is already built and already guarded.

SecondWhat the landing page has to give up

The landing page is the client-facing front door: a full-bleed hero, one sentence of credit, two bullets and a single call to action. It is deliberately uncluttered, and it is also mostly empty — the lower third and the right half carry nothing. That empty space is the budget.

What it gains

  • One entry point, one place to look, in every phase — landing, step 1, step 2.
  • Fixes a second problem nobody raised: mid-scenario the entry is a 32px glyph at the foot of a scrolling rail.

A softer variant: show the bar on the landing page only, and leave the rail’s glyphs to serve the workspace. That keeps the client-facing screens clean while still giving the admin a front door — at the cost of the console living in two places.

  • The most work on this page by a wide margin — and it does not make the landing link itself unnecessary.

A question every option inheritsWhat does the catalogue mean with no mandate?

Four of the five views are scenario-independent: sleeves, archive, activity and the register are about the library and the record. The catalogue is not — it prices each product against the open proposal’s schedule, level and account-size tier. Cold, it says so.

On the requirement“Only visible to the admin user”

Every option is wrapped in the check the rail bar already uses, and the same rule D62 set applies: render the whole device or none of it — an empty bordered strip is worse than no strip.

The gate

capabilities.canAdmin, served on the schema, which the landing page already fetches. No extra call.

The honest caveat

Client-side visibility is not access control. Anyone can type #repository. What makes it safe is that every endpoint sits behind requireAdmin and refuses — the hidden link is a courtesy, not a lock.

Worth deciding

What a non-admin who follows a shared #catalogue link should see. Today: the landing page, silently. A one-line “you do not have access to the library” would be kinder than a link that appears to do nothing.

FinallyWhat I would build

Option 1 now, option 5 next, and option 7 when the console’s width starts to hurt more than its front door does.

1

Start with the second card

RecommendedSmall

It is the only option that addresses the admin as an admin at the moment they arrive, costs a non-admin literally nothing, and takes about a day. The live counts on the card earn their place twice: they tell an admin the state of the library before they click, and they prove the store is reachable.

Then

  • Option 5 once the card exists to advertise it — the palette is the daily shortcut, and the card is what teaches it.
  • Option 4’s softer variant if reaching the console mid-scenario turns out to matter as much as reaching it cold.

Not yet

  • Option 6 is the better end state if admins outnumber their proposals — but build the card first and see whether the counts get used.
  • Option 7 is right eventually and wrong as a first move: it is a week of routing to solve a problem a day of front door solves.
One thing to settle before building any of them: where Close goes. From the landing the console already returns to the landing, which is right. If the card is the entry, the console should return to the landing too — not to a scenario the admin never started.
