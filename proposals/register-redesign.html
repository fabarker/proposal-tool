The readWhat gets in the way

Two jobs bring people here. Find: someone quotes a UID, a client name or a week, and you need that row. Read: you have the row and need what was delivered — the basis, the sleeves pinned, the workbook.

P1The Proposal UID is not in the table

It is the identifier everything else quotes — the workbook's file name, cell B1, the account opening request, the 404 message that tells a user to go and find one. In the register it appears only after you have opened a row, and then only as text you must select by hand.

Blocks: find
P2Opening a row costs you the list

The drawer takes up to 52% of the card's height from the bottom, so a four-row list becomes a two-row list the moment you look at anything. Comparing two proposals means opening, reading, closing, opening.

Blocks: read
P3The width goes to what repeats

On a real desk the same handful of PWAs and one or two books fill the register. Book prints PMG Multi-Asset Portfolio in full on nearly every row, while Proposal portfolio — the thing that actually varies — gets a narrow column of two words.

Blocks: find
P4Nothing can be sorted

The order is export time, descending, always. "The largest mandate this quarter" or "everything for this PWA oldest first" cannot be asked. The catalogue next door sorts on every column.

Blocks: find
P5The warning only exists inside the record

Whether a proposal's sleeves have moved or been archived since delivery is the most valuable thing the register knows — and it is visible only once you open that proposal. You cannot see at a glance which of thirty proposals have drifted.

Blocks: find, read
P6Large mandates print as nonsense

money() stops at m, so a 5×1014 mandate reads $500000000.0m. It is a real row in the register today, and it is wider than the column.

Blocks: find, read
P7Five dropdowns, all the same weight

By, PWA, Currency, Book, When sit in a row as equals, each needing a click and a read. The common questions — this week, mine, the big ones — take three interactions each and cannot be saved.

Blocks: find
P8No sense of the whole

The footer counts proposals and megabytes. With filters in force nothing says how much mandate they represent, how many PWAs, or what period — so the register cannot answer a question about a set, only about a row.

Blocks: read

Whichever you pickFixes that are layout-independent

These are worth doing under any of the five. Each says what it costs.

F1Put the UID in the table, and make it copy on click

A monospaced pr_1b8285460b7f column, click to copy, with a tick confirming. Front end only — the list already returns it. Answers P1.

F2Download the workbook from the row

The file is the thing most often wanted, and today it takes two clicks and a drawer. A download control on each row makes it one. Front end only.

F3Sort on Exported, Mandate and PWA

The list is already paged by an export-time cursor, so sorting by anything else has to be a server order, not a client one: a sort parameter on the endpoint. Modest backend work. Answers P4.

F4Flag moved sleeves in the list

The list already returns each proposal's pinned sleeves with their revisions; comparing them to the library's current revisions server-side gives a 2 moved badge per row. Modest backend work. Answers P5.

F5Teach money() billions and trillions

bn and tn above m. Six lines, and it fixes the same figure everywhere it appears. Answers P6.

F6A summary strip over the table

For the rows the filters currently select: how many, total mandate, how many PWAs, the span of dates. Recomputed server-side with the facets. Answers P8.

F7Keyboard: j/k, Enter, Esc

The catalogue already has a row cursor; the register has none, so a long list can only be used with the mouse. Front end only.

F8Show whether an account has been opened

Each proposal takes one account opening request (D76). The register is where you would look to see if it has one — today nothing in the console shows account requests at all. Needs a join on the account-requests table.

Five layoutsHow the page could be laid out

Each mock-up includes the fixes above where they are relevant, so the layouts can be compared as finished pages rather than as sketches.

01

Split: the list keeps its place

Recommended

The record moves from a drawer at the bottom to a pane on the right. The list narrows to what identifies a proposal — when, who, how much, the UID — and everything else moves into the pane, which scrolls on its own. The list never shrinks, so you can run down it reading records as you go.

What it gains

  • Answers P2 outright: reading a record costs no rows.
  • The card is 1400px wide and the record is a tall, narrow thing — this is the shape the content already has.
  • Moving Basis, Book, Portfolio and Pricing into the pane frees the list to show the UID and a status column instead (P1, P3).
  • Arrowing down the list with the pane open turns the register into something you can read through.

What it costs

  • The implemented table is wide; in a half-width pane its columns must drop to three.
  • Below about 1100px the split has to fall back to today's drawer.
  • Most work of the five: a second scrolling region, and the pane's own layout.
02

Banded by day

Small

The register is a chronological record, so let it read as one: a band per day — or per week beyond a month — carrying the date, the count and the mandate that went out. The same table, grouped, exactly as the catalogue bands by category.

What it gains

  • Answers what went out this week by reading, with no filter set at all.
  • The date leaves every row, so the first column becomes a narrow time.
  • Reuses the catalogue's banding, including fold-all — a known pattern and mostly known code (D100).

What it costs

  • Bands take vertical space, and on a busy desk a band per day may hold one row.
  • Does nothing for P2: the record still opens underneath.
  • Bands and sorting by mandate (F3) contradict each other; sorting would have to be within a band.
03

Two-line rows, expanding in place

Medium

Each proposal takes two lines: identity on the first, terms on the second in quieter type. Clicking does not open a drawer — the row itself expands, pushing the rows below it down, and collapses again. The list is never replaced, only interrupted.

  • Someone has to decide the set of views; wrong ones are clutter.

If you want oneRecommendation

01 with 04's saved views on top, and F1, F2, F5 and F7 taken first because they are front-end only.

  1. Start with the cheap fixes. The UID column that copies on click, a workbook control on the row, money() taught billions, and a keyboard cursor. No server change, and between them they answer P1, P6 and most of the friction in find.
  2. Then the split. It is the only option that fixes P2, and the console is already 1400px wide on this view — the record is a narrow, tall thing next to a list that wants to stay put. Below 1100px it falls back to today's drawer.
  3. Then saved views. Once the counts endpoint exists, This week, Sleeves moved and No account yet replace three dropdown interactions each with one, and the counts are worth reading on their own.
  4. F4 and F8 last, together. Both are joins the server does once per page: which sleeves have moved, and which proposals have an account request. They are what turns the register from a list of files into a picture of what is outstanding.

If only one thing ships, make it 04: it is the smallest change with the largest effect on find, and it does not foreclose any of the others. 02 is worth adding to whichever layout wins as a toggle rather than a default — useful for a weekly read, wasteful on a quiet desk.

Worth decidingOpen questions

  • Who is this page for? I have assumed an admin checking what was delivered and fetching workbooks. If it is also where someone reports on volumes, F6 grows into a proper summary and 02 becomes more valuable than 01.
  • Should the register show account requests at all? F8 assumes yes. It means the console reads a second table, and it makes the register the place you check whether an account was opened — a job nothing currently does.
  • What counts as a saved view? My five are a guess: This week, Mine, Sleeves moved, Over $100m, No account yet. Over $100m needs a mandate filter the endpoint does not have.
  • Is the drawer's second picture still wanted? Allocation and Implemented sit behind a toggle. In a right-hand pane there is room to stack them, which would remove a control and a decision.
