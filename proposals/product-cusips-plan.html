Product CUSIPs

How the catalogue can carry every CUSIP a product trades under, with its listing, domicile, UK reporting and issuer details, while staying one row per ProductId.

Written 20 October 2026Builds on D180–D184 (a product by base currency)Status for your decisions, nothing changed yet

The answer in brief

Keep the product exactly as it is: the ProductId is what a sleeve holds, what a fee group prices and what the register records. Give each product a list of CUSIPs beneath it, loaded from a file of its own with one row per CUSIP. The catalogue stays one row per product, and finds and filters through that product's CUSIPs. The product card gains a CUSIPs section that shows once what every CUSIP shares, and lays out only what differs.

The product stays the row

Nothing that holds, weights or prices a product changes. The catalogue, the sleeves, the fees and the proposals all keep using the ProductId.

CUSIPs hang off it

A new list per product, one entry per CUSIP, loaded from a CUSIP file. A few fields are fixed and checked. Every other column in the file is kept as it is.

The card shows the difference

What every CUSIP shares is shown once. A table shows where they differ, grouped by trading currency, with the CUSIP each base currency uses marked.

01What lives where

There are already two levels in the catalogue: the product, and the product as each base currency reads it (its ticker, minimum, exposure and issue currency there, D180–D184). CUSIPs are a third level, and they are not the same thing as the second. Two CUSIPs can both trade in dollars, one in New York and one in London. One CUSIP can be the right one for both a GBP and a USD proposal. So CUSIPs need a list of their own, not more columns by currency.

The rule that decides which level a field belongs to

If a field changes what the client holds or what it costs, it belongs to the product, or it means this is a different product. If it changes only where the product is bought and how it's reported, it belongs to the CUSIP. Share class is the test case. If the accumulating and distributing CUSIPs of a fund are one product today and their costs are the same, share class can stay on the product. If they differ in cost, they should be two products (question 4).

02Where the data comes from

From a CUSIP file, with one row per CUSIP and a ProductId column saying which product it belongs to. It is a separate file from the product file, imported on the Catalogue tab the same way: you see a preview of every change, and nothing is written until the whole file reads cleanly.

What an import does

  • Adds and updates CUSIPs by their CUSIP. The preview reads per product, for example: "GS Access Treasury: added H3611Q133; G3982W116 UK reporting No → Yes".
  • Leaves out nothing silently. A CUSIP missing from the file stays, unless you tick withdraw missing. A withdrawn CUSIP is kept on the record and drops off the card.
  • Refuses a CUSIP that moves to another product. That is almost always a mistake in the file. If it's real, withdraw the CUSIP and add it under the new product.
  • Also from the sleeve tool, beside the product commands: --cusips-import FILE and --cusips-export FILE.

03How it's stored

A new table, productCusips, in the same sleeves.db as the catalogue (schema 13). The CUSIP is the key and the ProductId says which product it belongs to. Each core field is a column. Everything else the file carried goes in one attributes column, as heading–value pairs in the file's order.

PartHoldsWhy
Core columnsISIN, SEDOL, ticker, trading currency, venue, listing country, domicile, UK reporting, issuer and issue country, issue currency, primary-forThese can be checked, filtered and linked to a base currency. A field the catalogue filters on has to mean the same thing on every row.
AttributesEvery other column, under its own headingCyrus's list of fields will grow. A new column in the extract then appears on the card with no code change and no update to Cyrus.
HistoryEach change to a product's CUSIPs, as an entry in that product's historyYou already read a product's story on its card. "CUSIPs updated from cusips.csv: added 1, changed 1" belongs there, not in a log of its own.

The product row itself does not change, so nothing that reads products today needs to know about CUSIPs.

04The catalogue

Still one row per product. CUSIPs reach the table in three ways:

  • Search finds a product by any of its CUSIPs: a CUSIP, ISIN, SEDOL or any CUSIP's ticker. The row shows the product. Its card opens on the CUSIP that matched, highlighted.
  • Filters on CUSIP fields, in their own group in the side panel: domicile, trading currency, venue and UK reporting. A product matches if one of its CUSIPs matches. With two filters on, for example UK reporting Yes and trading currency GBP, a single CUSIP must meet both. That answers the real question, "can this be bought in sterling with UK reporting?", rather than "does it have some UK-reporting CUSIP and, separately, some sterling one?". A row matched this way says which of its CUSIPs matched, for example "2 of 5 CUSIPs".
  • A CUSIPs column giving the count. It's one of the columns you can hide.

The table only needs a summary of each product's CUSIPs: the count, the identifiers to search, and the values to filter on. That summary comes with the catalogue. A CUSIP's full details are read when its card opens, so the catalogue stays fast however many fields the file carries.

05The product card

A CUSIPs section, below the figures and above Used in. It reads from the top down:

  1. One line of summary. How many CUSIPs, the currencies they trade in, how many report in the UK, and where they're domiciled.
  2. Used for. The CUSIP each base currency uses (its PrimaryFor). A currency the product is offered in with no primary is flagged.
  3. Same on every CUSIP. The fields that are identical everywhere, shown once. Usually that's most of them, such as issuer country and issue currency.
  4. The table. One row per CUSIP, grouped by trading currency, with a column only for a field that differs between them. Selecting a row opens everything that CUSIP carries, the file's extra columns included.

06The link to base currency

The product file already gives each base currency its own ticker and issue currency (D180–D184). The CUSIP file's PrimaryFor says which CUSIP that currency uses. To begin with, the two are checked against each other rather than one replacing the other:

  • Where the product's GBP ticker isn't the ticker of its GBP primary CUSIP, the card and the import preview say so: GBP ticker GBIL · primary CUSIP's GBIT. The same goes for issue currency.
  • Proposals keep printing what they print today.

Once the two agree everywhere, a later step can let the primary CUSIP supply the ticker and issue currency for each currency, so they're kept in one place and the product file no longer repeats them (question 5). The minimum investment stays with the product file. It is PMG's rule for a position, not a property of the security.

07Proposals, later

None of the above changes a proposal. When you want a proposal to say exactly which security to buy, two things follow:

  • Printing it. The implementation sheet gets a CUSIP column beside the ticker, filled from the base currency's primary CUSIP. The register records the CUSIP used for each product, so a delivered proposal says what was meant, even after the file changes.
  • Choosing it. If some proposals must use a different CUSIP from the primary one, for example a UK-taxpayer client needing UK reporting, that is a rule over the CUSIP fields: "for GBP proposals, prefer UK reporting". It's the same kind of rule a sleeve's editions already use. Whether you need it at all is question 6.

08Why it's built this way

The design follows from one fact: the product is the unit that carries meaning in the tool. Sleeves hold products at weights that add to 100%. Fee groups price products. Minimums are checked per product. Overlay rules and the register name products. A CUSIP changes none of that. It is a way to buy the same exposure. So the plan adds CUSIPs beside the product and leaves every existing path alone. These are the alternatives, and why each loses:

One catalogue row per CUSIP

Every product would appear five or six times. A sleeve editor could pick the wrong row, the same exposure would be counted under several identities, and every sleeve, fee and register entry would have to move to a new key. It is also exactly the catalogue you said you don't want.

More columns by currency, like Ticker USD … Ticker EUR

That pattern suits four currencies and four fields. CUSIPs aren't keyed by base currency: two can trade in dollars, and the fields are an open list. It would mean a fixed grid of columns that's empty where nothing applies and still can't hold the next field.

One free-form block of text per product

Easy to load, but it can't be checked or filtered, and it can't say which CUSIP a GBP proposal uses. The plan keeps the free-form part for the extra fields only, where those limits don't matter.

Typing CUSIPs in on the console

The security master in Cyrus owns this data, and hand-kept copies drift from it. Loading from a file keeps the tool a faithful copy. The card shows the data but doesn't edit it, at least at first (question 7).

Making the CUSIP the product's key

CUSIPs come and go as listings are added and dropped, while the product, and every sleeve holding it, stays. A key has to outlive what it identifies.

Three smaller choices follow the same reasoning:

  • A file of its own. The CUSIP data has a different owner and a different rhythm from the product file. PMG curates the product file. The CUSIP file can be an extract straight from Cyrus with nothing reshaped. Keeping them apart means neither has to repeat the other.
  • Filters matched on one CUSIP. Two filters are answered by a single CUSIP that meets both, because the question being asked is always about one security you could actually buy.
  • Shared fields shown once. CUSIPs of one product agree on most things. Showing every field for every CUSIP would hide the two or three that differ, which are the ones you open the card to see.

09In phases

Each phase is one update for Cyrus and leaves the tool complete and working. Proposals don't change until phase 4.

1

Store, import and show

  • The productCusips table (schema 13).
  • The CUSIP file's import, with its preview, on the Catalogue tab and in the sleeve tool, plus its export.
  • The CUSIPs section on the product card, and search by any identifier.
  • History entries on the product.

On Cyrus: one update and a schema move. Nothing shows until a CUSIP file is imported.

2

Find by CUSIP

  • The CUSIP filter group, matched on one CUSIP.
  • The CUSIPs count column.
  • The compare view's CUSIP row.

On Cyrus: page files only.

3

Primary by base currency

  • PrimaryFor checked and shown.
  • Warnings where a primary CUSIP and the product file disagree.
  • Optionally, the primary CUSIP supplies the ticker and issue currency for its currency.

On Cyrus: one update. The optional step changes what the product file must carry, so it waits for your yes.

4

CUSIPs in proposals

  • The CUSIP column on the implementation sheet.
  • The CUSIP recorded in the register.
  • Rules for choosing a CUSIP, if you want them.

On Cyrus: one update and a register schema move.

10What I need from you

  1. Where does the CUSIP data come from?A Cyrus security-master extract, a spreadsheet, or something else? Does it already carry the ProductId, or only a ticker or name to match it by? If it's an extract, a sample row with its real headings would settle the column names.
  2. Is the key always a true CUSIP?Or sometimes a CINS, an ISIN or an internal Cyrus security id? The plan takes the key as given and checks a CUSIP's check digit only when it looks like one.
  3. Which fields should be filterable?The plan's core list is ISIN, SEDOL, ticker, trading currency, venue, listing country, domicile, UK reporting, issuer and issue country, and issue currency. Anything else would be shown and searchable, but not filterable.
  4. Do share class or hedging vary between one product's CUSIPs?If they do, and the cost differs, those CUSIPs are probably separate products.
  5. Should the primary CUSIP eventually supply each currency's ticker and issue currency?That keeps them in one place, but it changes what the product file has to carry.
  6. Should proposals name the CUSIP, and do any proposals need a CUSIP other than the primary one?For example, UK reporting for UK-taxpayer clients.
  7. File only, or editable on the console?The plan starts with the file only, because the security master is the source. Marking the primary CUSIP on the card would be the first thing to make editable, if you want it.
