Controlling how the tactical tilt and the volatility premium are funded

Today both overlays are wired into the code: the Tactical Tilt Fund takes 8% of the portfolio from Investment Grade Fixed Income, and the Strategic Volatility Premium then takes 7.5% of what Investment Grade Fixed Income has left. This page proposes a repository tab, Overlay Funding, where each overlay's size and its sources (any categories, in any proportions) are set, noted and kept in history, the same way the Uncalled Capital Allocation split is.

3 · The plan

Data model

Reuse D148's store rather than invent one: fundingSplit.py already keeps policies in sleeves.db (policies and policyHistory, a kind column, a house scope * with per-implementation-type overrides, weights to 4dp summing to exactly 100, a note and user per save, history and revert). One new kind, overlay, holding an ordered list of rules per scope — any number of them, resolved strictly top to bottom, each reading the allocation as the rules above it left it. Each rule holds:

The currency restriction on SVP stays a code rule, not a policy field: it is a product constraint, not a funding choice.

Validation (server, and mirrored live in the tab)

  • Size > 0; for portfolio basis at most 25%, for source basis at most 50% (guards against a typo, adjustable).
  • Weights 0–100 at 4dp, summing to exactly 100; no duplicate source; a source cannot be the overlay's own category.
  • Every source must be a category held by every portfolio in scope that can take the overlay (the same eligibility rule as D148). A rule naming Hedge Funds is refused for a type whose ex-Alts portfolios would take it.
  • No overdraw: the server runs the whole list over every portfolio in scope, top to bottom, and refuses it if any source would go below zero; it warns (not refuses) below 2%. The worst case is named in the refusal (USD Conservative ex-Alts: Other Fixed Income would be −0.4%).
  • Where a portfolio cannot fund a rule that is valid for the type (say a source is held too thinly), the toggle is disabled for that portfolio with the reason, as All Equity is today.

Where it is read

  • rules.py: tiltedCategories and volPremiumCategories become one generic applyOverlay(categories, rule); implementedCategories folds it over the scope's list in ordinal order, each call receiving the previous one's result. A rule whose overlay is not selected for the proposal is skipped and the next one reads what the last applied rule left. The constants stay as the seed and the fallback when the store is unreachable.
  • schemaPayload serves the resolved policies (as _servedFunding does for D148), so the page's JavaScript mirror reads the same numbers; the mirror gains the same generic function, and the Python/JS parity test covers multi-source rules.
  • workbook.buildImplementationRows, the deck and the register need no change beyond receiving the resolved policy, because they already consume implementedCategories.
  • The screen's notes (Tactical tilt added, funded from …, core.js:845; the premium's note, implementation.js:681) and the deck's footnotes read the sources in words: funded 5% from IGFI and 3% from Public Equity.

Register and audit

Each proposal records the overlay rules it was built under (a new overlayFunding column, register schema 5; TTF 8% portfolio: IGFI 100 · SVP 7.5% source: IGFI 100 · order TTF→SVP), so a later rule change never silently alters an issued proposal's explanation. The history on the tab is the audit trail; revert re-saves an earlier version with a note.

Migration

Sleeves schema 5 → 6 seeds the house rules to reproduce today exactly. A test builds every baked portfolio with every overlay combination under the seeded policy and under the old constants, and requires identical weights to 1e-9, before and after, in Python and in the JavaScript mirror.

Tests

  • Seed parity (above); the two orders; multi-source portfolio and source bases summing to 100 after the move.
  • Refusals: sum ≠ 100, source not held by every portfolio, overdraw with the worst case named, 4dp.
  • Override precedence (type over house), remove override, history and revert, as test_funding_split.py does.
  • Routes: GET/PUT /scenario/repository/overlays, POST …/overlays/remove, GET …/overlays/history, POST …/overlays/revert (five, 42 in all).
  • The page guard: no book in the tab's strings (D150).

Phases

  1. Store and engine. The overlay kind as an ordered list (ordinal per rule), seeding migration, generic applyOverlay folded over the list in Python and JS, schema payload, parity tests. No visible change.
  2. The tab. Overlay Funding as option 8: rule cards in resolution order, drag or ↑ ↓ to reorder, add and remove rules, the editor drawer (name, row, size, basis, sources), the step-by-step resolution trace, validation with the worst case per step, note, save, history, revert.
  3. Overrides and records. Per-implementation-type overrides, the register column, notes and footnotes in words.
  4. Optional. Currency or risk-level scopes; asset-class-level sources.

Open questions

  1. Category or asset class? Sources at category level keep the rule valid across portfolios whose assets differ; asset-class level (e.g. only US Dollar Debt) is finer but more often unfundable. Recommend category level first.
  2. Basis per overlay, or fixed? Keep today's pairing (TTF as a percent of the portfolio, SVP as a percent of its source) as the default, but let both switch?
  3. Where does the premium go? Today it sits straight after IGFI. With several sources, after the largest source, or a fixed place?
  4. Order. Is premium, then tilt ever wanted, or should the order stay fixed and only be shown? Answered: the order is editable — the rules are an ordered list, dragged into place, resolved top to bottom (option 8).
  5. Unselected rules. When a proposal does not select an overlay (no tilt), the plan skips its rule and the rules below read the allocation as it stands. Confirm that rather than, say, refusing a later rule that was sized on an earlier one.
  6. Scope. Are per-type overrides enough, or do you need currency or risk-level rules too?
  7. Existing proposals. A saved scenario rebuilt after a rule change will move; should reopening an issued proposal keep the rule it was issued under?
