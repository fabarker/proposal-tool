Proposal · Front end

Moving the Proposal Tool to React

How I would refactor the page and the repository console onto React without stopping feature work, without breaking the Cyrus port, and without losing the behaviour the last 158 decisions encoded.

Where the front end is today

  • About 780 KB of hand-written JavaScript in four files: core.js (196 KB), implementation.js (135 KB), repository.js (440 KB) and picker.js (8 KB). generator/build_styles.py concatenates them into one bundle and writes it, with the CSS from the Python modules, into proposalTool/static and the service mirror.
  • Rendering is string templates set with innerHTML (about 80 call sites), with document-level delegated event handlers keyed on data-* attributes.
  • State is global mutable objects (state, repo, sv, nc and others). After a change, code calls a re-render, then restores focus and scroll by hand (preserveFocus, svFocusNow, the scroll snapshots).
  • Much of the careful work is UI plumbing React would own: the unsaved-changes guard (goTo), focus traps, inert backgrounds, row enter/leave animation (animateRowChanges), measured column widths (sizeFixedColumns), the docked column heads.
  • Pure logic is already separated in places and tested in node from Python (the overlay resolver, the sleeve view helpers, the edition grid mapping). That is the most valuable thing to carry over intact.
  • The host is fixed. The page is a static folder served by the Cyrus dashboard, the API is the Python router, and porting means copying three places. Any React build must still produce plain static files.
The honest question first. The tool works and is well tested. React pays off here through fewer state and focus bugs (most review findings in D155–D158 were exactly that), easier onboarding, and components shared between screens. It does not pay off as a rewrite. The plan below is incremental, and every step leaves a working, shippable tool.

Keeping what already works

  • Port the pure helpers first, unchanged in behaviour. The Python tests that run JS in node (overlay parity, the sleeve view helpers, the edition fuzz) are pointed at the compiled domain/ module. Those tests passing is the definition of "ported".
  • Keep the server unchanged. React is a client change only. The routes, the 409s, the funding and overlay stores and the register stay as they are.
  • Write the decisions down as tests before moving each screen. For example: equal column widths, a total of exactly 100%, the guard on every move away from an edit, Escape order, and that the page never says "book". Many already exist as source-reading tests. These become component tests, so a decision cannot be lost silently.

Phases

0

Scaffold beside the old page

Vite and TypeScript in web/, a typed API client generated from the router's payloads, the domain modules ported with the existing JS-in-node tests pointed at them, and CI building both bundles. Nothing user-visible changes.

1

Mount React islands, newest screens first

The repository console tabs are the most self-contained and the most recently specified. Overlay Funding, then New sleeve and New edition, then Sleeves (Cards | Table), each rendered by React into its existing container while the rest of the page stays as it is. The old and new code talk through one small bridge for the open scenario and the "open this sleeve" deep links.

2

The rest of the console

Catalogue, Archive, Activity, Proposals and Uncalled Capital Allocation. After this the 440 KB repository.js is gone, and with it most of the hand-written focus and guard code.

3

The proposal page

The rail, allocation and risk tables, charts, then the implementation step. These come last because they carry the most bespoke layout: measured columns, docked heads, row animation. Each gets a visual check against screenshots of today's page before the old code is removed. The Excel and PowerPoint outputs are server-side and are untouched.

4

Remove the generator's JS path

build_styles.py keeps writing the HTML shell and the theme CSS, or hands those to Vite too. The Cyrus porting guide changes from "copy the generated bundle" to "copy the built folder", which is the same copy.

Effort, roughly. Phase 0: a few days. Phase 1: one to two weeks per console screen. Phases 2 and 3: about the same again for the rest. Feature work can continue throughout, because each new or changed screen is simply written in React from then on.

Risks and how to handle them

RiskMitigation
The Cyrus host or the managed browser estate can't take a new runtime or larger bundleReact and ReactDOM add about 45 KB gzipped against roughly 780 KB of source today. Ship a single static bundle with no CDN dependency. Confirm the supported browser versions before phase 0.
Subtle behaviour lost in translation (rounding, ordering, Escape order, focus targets)Logic ported first with its parity tests, decisions captured as tests per screen, and the Playwright flows re-run on every change.
Two systems in one page during the migrationOne narrow bridge (open scenario, deep links, the unsaved guard across islands). Retire each old screen as soon as its React version ships.
Visual driftCSS Modules reuse today's tokens, plus screenshot comparisons for the allocation, risk and implementation tables.
The Python and JS parity checks (overlay resolver, edition rules) divergingKeep the node-run parity tests, now pointed at the TypeScript modules, in the Python suite.

What I would not do

  • Rewrite everything at once, or pause features to do it.
  • Move logic out of Python. Pricing, rules, funding, overlays and the deck stay server-side.
  • Add server-side rendering or a Node server. The host serves static files and the Python API.
  • Introduce a component library that replaces the house look.

A first step to prove it

Build the Overlay Funding tab in React as an island: it is self-contained, recent and well specified (D155), and has a parity test with Python. If that ships cleanly in the console beside the existing tabs, and the Cyrus port is still a folder copy, the approach is proven at low cost.
