Proposal Tool · Design proposal for review

Guiding the first build

After the mandate dialog closes, the PWA lands on an empty workspace and has to work out that the next move is in the rail. Six ways to make that obvious, each with a working mock-up, and a recommended combination.

Scope step 1, from mandate to first columnBranch sleeve-editionsStatus for review, nothing built

What the PWA sees today

This mock-up behaves like the tool does now. The rail on the left holds five choices across two sections. The document on the right shows one dashed box. Answer the rail to see what changes, or press Play through.

The box names the wrong step

It says “pick an allocation and risk level”, but those are the fourth and fifth choices, and they are locked at this point. The only controls that work are Base Currency and Currency Hedging, then Implementation Type. A PWA who follows the text finds a greyed-out select.

It sits far from the controls

The box is centred in the document, several hundred pixels from the rail. The eye lands on it, reads “in the rail”, and then has to search. Nothing points to where to go.

It looks empty, not actionable

A dashed border, grey copy and no button is the usual look for an empty placeholder. It reads as a page that hasn't loaded yet, not as a task to do.

The rail cue is too faint and too broad

A faint pulsing ring outlines a whole section, not the field to fill. Nothing says there are five answers, or that the second section stays locked until the first is done.

What good looks like

Three principles, used to judge every idea below.

One next thingAt any moment exactly one control is marked as next, and it's the same control wherever it's mentioned.
Point from where they lookThe instruction lives where the eye lands, in the document, and leads to the exact control in the rail.
Show what's being builtEach answer visibly moves something, so the PWA can see the base portfolio taking shape before it exists.

Six ideas

Each idea stands alone, and most combine. Every mock-up works: use the selects, press Play through for the whole flow, or Reset to start again.

  • ANumber the path in the rail
  • BA checklist instead of the box
  • CA line from the document to the field
  • DA preview column that fills in
  • EFocus moves to the next field
  • FDim the document until setup is done
A

Number the path in the rail

Small buildRail only

Turn the five fields into a numbered path. A segmented bar under the brand counts the answers. The one field to fill next gets a light-blue marker and a Next tag, so the cue sits on a field instead of ringing a whole section. Locked fields say what unlocks them.

How it works

  • Numbers 1–5 run across both sections, so the order is visible before anything is touched.
  • An answered field turns its number into a tick. The Next tag moves on.
  • If the risk level is All Equity, Allocation drops out and the count falls to four.
  • This replaces the section ring (tier-ring) and uses the same colour, --rail-focus.

Watch for

  • On its own, it still depends on the PWA looking at the rail. It fixes the rail's clarity, not the document's pull.
  • Once the base portfolio exists, the numbers and tags should go away. An experienced user editing a built base doesn't need a route.
B

A checklist instead of the box

Small–medium buildDocument + rail

Replace the dashed box with a card that lists all five choices in order, shows each one's answer or what locks it, and gives the next one a Choose button. The button moves focus to that exact field in the rail and flashes it. The document stops describing where to go and takes the PWA there.

How it works

  • The card and the rail read the same state, so they can't disagree.
  • Choose focuses the rail's select. The flash confirms where focus went.
  • The progress line (“2 of 5”) can be announced to screen readers with aria-live="polite".

Watch for

  • The same five answers now show up twice. That's acceptable only while the base portfolio doesn't exist yet; the card disappears when the table arrives.
  • It's still a card of text. It explains the task well but doesn't show what the answers will produce.
C

A line from the document to the field

Medium buildFragile when narrow

The prompt card sits in the document and a dashed line runs from it across into the rail, ending at the field to fill next. As each answer lands, the card slides down and the line moves with it. It's the most literal “look here”.

How it works

  • The line is drawn by measuring where the field and the card sit and redrawing on every change and resize.
  • The card lines itself up with the target field, so the line stays short.

Watch for

  • Below 1040px the rail stacks above the document (spec §6), so there's no side-by-side line to draw. It needs B or D there anyway.
  • It has to be remeasured on resize, rail collapse and scrolling. That's the most code for the smallest gain over B's button.
  • A line across the page's edge is loud. It suits a first visit, not every visit.
D

A preview column that fills in

Medium buildDocument

Replace the empty box with the allocation table itself, in outline. The seven category rows are there with loading bars. The base portfolio's column header is a row of empty slots (currency, hedging, implementation, risk, allocation) that fill one by one as the rail is answered. The next empty slot pulses. When the last one fills, the loading bars become figures. The PWA can see what they're building while they build it.

How it works

  • The category rows come from the schema already loaded for the rail (categories), so the outline is the real table's shape, not a picture of it.
  • The line above the table (“Next: Base currency in the rail”) is a button, doing the same job as B's Choose.
  • The table already has a blue top border (accent-top). The outline gives that frame something to hold, so the fix that hid it today can be reverted.

Watch for

  • The loading bars must look different from a column that's loading after a change (spec §10.1). Here they're still, with no header figures. A resolving column shows its name.
  • The slots use short labels (“PMG Multi-Asset”). The full name stays in the rail.
E

Focus moves to the next field

Small buildBehaviour, not layout

When Continue closes the mandate dialog, keyboard focus goes straight to Base Currency. Each answer moves focus to the next field that's open. The PWA's eye follows the focus ring down the rail, and a keyboard user never has to Tab through controls they've already answered. Press Replay from mandate to see focus land. The demo moves focus from its own buttons only, never when the page loads.

How it works

  • After the relevant change handler re-renders, it focuses the next field with preventScroll, if that field is open.
  • After the mandate is committed, focus goes to #ccy, not back to the Start button.

Watch for

  • A native select can't be opened from script. Focus lands on it, and the PWA still clicks it or presses Space.
  • It must only run while no base portfolio exists. Moving focus after edits to a built base would feel like the page taking control.
  • Screen readers will read each new field aloud as focus lands. That's good here, since it's the next question, but it's another reason to stop after the first build.
F

Dim the document until setup is done

Small buildNot recommended

Dim the document under a navy overlay while the setup is incomplete, leaving the rail as the only lit surface. A short message points left. The overlay lifts when the base portfolio exists.

Why it's here

  • It's the strongest possible cue. Nobody misses it.

Why not

  • It treats every visit as a first visit. PWAs will build dozens of proposals, and after the second one it's an obstacle.
  • It hides the stage title and step nav that tell the PWA where they are.
  • It fights the page's existing modal. The mandate dialog has only just closed, and a second overlay reads as another dialog.

Recommended: A + D + E

The rail becomes a numbered path with a single Next marker (A). The document shows the base column filling in, with a link to the next field (D). Focus moves on with each answer (E). Each covers a gap the others leave: A makes the rail readable, D gives the document something to show, E connects the two without extra UI. All three turn off once the base portfolio exists, so repeat users see none of it after their first column.

All three together. Try picking All Equity as the risk level: Allocation drops out, the count falls to four, and the empty slot disappears from the column header.

Fix the copy now, whatever is chosen

The box's text names the wrong controls. That's a small change that can go in today. It becomes the prompt line in D later.

TodayChoose a base portfolio. Pick an allocation and risk level in the rail to build the first column.
Basis not setStart with the scenario basis. Choose a base currency and hedging policy in the rail.
Basis set, base not builtNow the base portfolio. Choose an implementation type, then a risk level and allocation.

How it would be built

  1. Copy by stateChange the #doc-empty text in build_styles.py so renderAlloc in js/core.js can set it from state.basisChosen. Can ship first, on its own.
  2. Numbered rail (A)Add numbered markers, the Next tag and the “unlocks after” notes in renderBasis and renderBase. A small helper, nextSetupField(), reads the same gates those functions already use (state.basisChosen, state.variant, the pending risk and allocation) and is the only place that decides what's next. Remove tier-ring. Styles go in pickers.py.
  3. Preview column (D)A new renderGhost() takes over renderAlloc's empty branch. It draws .tbl.alloc with the schema's categories and the slot header. Undo today's accent-top hide, since the frame now has a table. The prompt line calls the same focus helper as E.
  4. Focus moves on (E)In the change handlers for #ccy, #hedge, #bpv, #bpr and #bpa: after re-rendering, and only while no base exists, focus nextSetupField() with preventScroll. commitMandate ends by focusing #ccy.
  5. Record itSpec §10.2 (the empty state) and §13 (focus), plus a new DEVIATIONS entry. D's loading bars also need a line in §10.1 to separate them from a column that's loading.

For you to decide

  1. D or B for the document? D shows more and does more, but it adds a new state to the table. B is simpler and says more in words.
  2. Should guidance return after the base is deleted? My suggestion: yes. If the workspace has no columns, the PWA is back at the start and the path shows again.
  3. Should the rail's count include the mandate? It's answered in the dialog before the rail appears, so counting it would start every PWA at “1 of 6” with a tick already in place. My suggestion is to leave it out.
