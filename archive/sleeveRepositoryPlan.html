Proposal Tool · design note

Sleeve Repository

Move sleeves out of a Python file and into a database the app manages, put the products they are built from into a catalogue table, and give a small set of admins a console to build and maintain sleeves from inside the tool.

2 September 2026Status: built 2 September 2026, as specified belowRecorded as D56 and D57 in DEVIATIONS.md

What is being asked

  • Sleeves come from a database, the way strategic portfolios come from the supplying database's extract (D54) — not from tables hand-written in sleeves.py.
  • Sleeves are manageable inside the app. A repository where a sleeve can be built for a given category: created, edited, retired.
  • Only a special admin can reach that repository. Ordinary editors go on choosing sleeves; they never see the console.
  • Products come from a database too — one table, one row per product, one column per field — and building a sleeve means selecting products from that table, not typing them.

Where things stand today

Everything is in one file, service/cyrus_pmg/pmgService/scenario/sleeves.py: four libraries (one per Implementation Type) expressed as a BASELINE table plus per-type deltas, 56 sleeves, 73 distinct products written inline with their eleven fields. Import-time checks prove every sleeve's weights sum to 1, no name repeats, and every product's fee group is one the fee card prices. The public API is three functions — listSleeves(category, variant), sleeveExists, variantExists — and that narrow contract is what makes this change contained: the workbook, the rules, all three adapters and the bake call those three and nothing else.

Two facts from the survey shape the design. First, the same product appears in several sleeves (37 of the 73 do) with identical attributes every time — so products are genuinely a separate table, not sleeve-local rows. Second, 38 of the 73 products have no ticker (SMAs and private-market programmes), so a ticker cannot be the product key; the catalogue needs an id column of its own.

1 · Products: a delivered table, read like the portfolios

A new extract folder productSource/ with products.csv and products.xlsx, exactly the pattern of saaSource/. Columns:

ColumnMeaning
ProductIdThe key sleeves reference. Slugs of the names in the stand-in; the real catalogue brings its own ids.
Name, TickerTicker may be empty; it is served as the em dash the table already shows.
AssetClass, Style, Vehicle, Source, Liquidity, ExposureCurrencyThe attribute columns of the implementation table, as they are today.
ProductCostNumeric, per cent. Non-negative.
FeeGroupMust be one of the groups the fee card prices, checked at load — otherwise it would fail at export, under RDR, long after the product was placed.

The reader (scenario/products.py) exposes all(), get(id), has(id), describeSource(), and raises BadCatalogue on a missing column, duplicate id, empty name, bad cost or unknown group. A product it serves carries the same field names a sleeve product has always carried, so nothing downstream can tell where it came from.

Read-only in the app. The brief says select from the product database, not edit it — so, like the fee card, the catalogue changes by delivery. A product editor is additive later if wanted.

2 · Sleeves: a real, writable database

A SQLite file (SCENARIO_SLEEVES_DB, default service/var/sleeves.db), stdlib only, transactional, host-swappable. Two tables:

sleeves

id · variant (Implementation Type) · category · name · note · createdBy · createdAt · updatedBy · updatedAt
Unique on (variant, category, name).

sleeveProducts

sleeveId · position · productId · weight (fraction)
Primary key (sleeveId, productId). Cascades on sleeve delete.

A database that does not exist yet is created and seeded from sleeveSource/sleeves.csv — today's 56 sleeves written out row by row (Variant, Category, Sleeve, ProductId, Weight). After that the database is the library and the seed is never read again. The same shape is the interchange format: sleeveTools --export / --import move a library between environments or put it in front of someone as a table.

A sleeve stays keyed by Implementation Type + Category. The type decides what a category offers and what those sleeves contain (D29) — a US Onshore book reaches SMAs, an Irish Onshore book reaches UCITS — so the console is always working under one type.

3 · Admin: a third role

Beside PMG_ALLOWED_KERBEROS, a second list PMG_ADMIN_KERBEROS. In accessControl.py (the host seam, already carrying requireAuth and requireEditor) a third dependency, requireAdmin, gates every repository endpoint with a 403 for anyone else. The page learns whether to show the entry through the schema — capabilities.canAdmin next to the existing canEdit — so the UI hardcodes nothing and a non-admin never sees a control they cannot use.

What does not change

  • The rail's sleeve pickers, the implementation table, the donuts, the workbook, the fee resolver, the bake store — all read listSleeves() and see the same shape they see today.
  • VARIANTS (the four Implementation Types) stays configuration, not data. Adding a fifth is a one-line change as now.
  • The auto-attach rules for Tactical Tilts and the Strategic Volatility Premium: they look up their category's single sleeve, which the fixed-category rule guarantees.
  • Nothing about the transplant recipe: two verbatim copies and two inserts. The new pieces are one more file in the package, one more dependency in accessControl.py, and three environment values.

Decisions I have made, and the ones that are yours

1
SQLite for the sleeve store.

A writable, transactional, stdlib database in one file; the host points SCENARIO_SLEEVES_DB at its own path or swaps the store module for its database behind the same functions. The alternative — JSON files like the scenario spool — is simpler but is not a database and handles two admins saving at once badly. Recommended: SQLite.

2
Products read-only in the app.

Delivered as a table, like fees and portfolios; changed by delivery. If you want products created and edited in the console too, that is a fourth pane and a write path — additive, but it roughly doubles the console. Assumed: read-only, catalogue changes by delivery.

3
Sleeves keyed by Implementation Type + Category.

As today (D29). A sleeve shared across types is entered under each; the provenance line shows where else the same name is offered. A later "copy to another type" action is cheap if wanted. Assumed: keep the per-type model.

4
Entry points.

Rail brand block and landing page, admin-only. The user chip at top right is painted by the host's accessGate.js, so putting the link there would mean a host change. Recommended: rail + landing.

5
What a retired sleeve does to an open scenario.

Proposed: the scenario keeps the name; the picker shows its existing "no longer offered" state and the column's completeness gate stays open until a PWA re-picks. No silent substitution. Proposed: flag, never substitute.

6
Audit.

Provenance (who, when) on every sleeve is in scope. A full change history (every version of every sleeve) is not — it is a straightforward addition (a sleeveHistory table written on every save) if you want it from the start.

Data caveat, unchanged by this work. Every product and every sleeve in the seed is stub data — the authored library of D9 and D29. The three non-Multi-Asset libraries in particular are invented, and the fee groups on products were assigned by rule of thumb. The repository is the mechanism by which PMG replaces them; it does not replace them itself.
