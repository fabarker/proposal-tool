Service Down Pages

Seven treatments for what a PWA sees when the scenario service is not answering — built against what actually fails in this stack, not a generic 500 page.

3 September 2026Status: F and G built — 3 September 2026 (D64)Behaviour verified against dashboardFrontend.pyAudience: internal, professional, in a hurry

What actually fails, and what the user sees today

Three distinct outages, and only one of them is a page you can design:

What is downWhat happens nowCan a page help?
The scenario service
FastAPI, port 8002		 The Flask frontend still serves the page. Every /api call returns 502 with {"error": "The scenario service is not reachable. Start it and try again."}. The page shows a bare panel: “The Proposal Tool could not load” with a Retry button. Yes — this is the one. Everything below is a treatment of this state.
The service is slow
past the 300s proxy timeout		 504, same panel, same wording. A five-minute wait then a generic failure. Yes, and it deserves different words from “not running”.
The frontend itself
Flask, port 8001		 Nothing serves. The browser shows its own connection error. Only from a load balancer or reverse proxy in front of it — a static file the host serves, not something this app can render. Option E is written to be exactly that file.

So today's answer is a single grey panel that says the same thing whichever of the first two happened, offers one button, and tells the user nothing about whether their work survived.

What a good one has to do

Say whose fault it is

The first question a professional asks is “is it me?”. The page must answer that in its first line, so nobody wastes two minutes clearing cookies.

Say whether the work is safe

Scenarios live server-side for 24 hours, keyed by an id in the URL. Nothing typed is lost when the service drops — but only this page can say so, and it is the thing the user most wants to know.

Recover without being asked

/health is cheap and public. A page that polls it and comes back by itself turns an outage into a pause. A Retry button that must be clicked turns it into a chore.

Give something to report

Internal users escalate. A timestamp, the failing endpoint, the status code and a copy button save a round of “what did it say exactly?”.

Distinguish down from degraded

The tool can serve every portfolio from the bake with no database at all. A partial outage should not present as a total one — that is Option F.

Stay in the tool's own voice

Same masthead, same type, same restraint. An error page in a different visual language reads as a different system, which is its own small alarm.

Seven options

Option A

The notice

The current panel, written properly. Masthead kept, one status pill, one sentence of cause, one of consequence, a Retry and a way back. No diagnostics, no polling.

Optimises for

  • The smallest possible change — this is a rewrite of one existing block.
  • Calm. Nothing moves, nothing counts down.

Costs

  • The user must act to find out whether it is back.
  • Nothing to report with.

Option B

The diagnostic

Everything in A, plus a details block carrying the endpoint, the status, the reason the proxy gave, the time and a reference — with a copy button, so an escalation is a paste rather than a description.

Optimises for

  • Escalation. The first reply to any internal outage report is “what exactly did it say?”, and this answers it.
  • Trust: showing the real error reads as candour, not noise, to this audience.

Costs

  • Raw text on a client-facing surface — fine internally, wrong if a client ever sees the screen.
  • Still needs a human to click.

The Reference is generated client-side per failure — nothing correlates it to a server log today, so it identifies the report, not the request; making it a real correlation id means the proxy returning one. “Report to…” is a mailto: with the block pre-filled, unless there is a ticketing endpoint to point at.

Option C recommended

The self-healing wait

The page polls /health on a backing-off interval, shows what it is doing and when it will next try, and reloads itself the moment the service answers — landing the user back on the scenario they had open. The details block from B sits behind a disclosure for when someone needs it.

Optimises for

  • The common case, which is a restart or a deploy lasting a minute or two: the user reads a sentence, and the tool comes back on its own.
  • Answering “is it back yet?” without anyone clicking.
  • Saying the one thing that matters most — the work is safe — where it is impossible to miss.

Costs

  • Polling from every open tab. Needs a backoff and a ceiling, or an outage becomes a small load test.
  • Motion on an error page has to be restrained, and must respect prefers-reduced-motion.

Assumptions, and one confirmed defect. /health on the frontend is public and cheap to poll — but it is return jsonify({'status': 'ok'}) and never touches the backend, so it answers “ok” throughout an outage. Polling it as it stands would never recover. This option needs either a health route that proxies the backend's own, or a poll against a real endpoint such as /api/scenario/schema. The named proposal comes from the scenario id already in the URL, cached in localStorage at the last successful render — without that cache the strip says “Any proposal you had open is saved server-side” instead. Suggested backoff: 3s, 5s, 8s, 13s, 21s, then every 30s to a ceiling of 15 minutes, then stop and offer the button.

Option D

The status board

A component list with a state each: the page, the scenario service, the analytics library, the delivered data. Tells the user which part is down and therefore what still works.

Optimises for

  • Partial outages, which are the common real ones: the bake is fine but the database is not, or the analytics library will not import.
  • Being the page that also serves engineering during an incident.

Costs

  • Every light needs something to read it from. Today only two of these four can be known from the browser; the rest need a health endpoint that reports components.
  • A board of red lights is more alarming than one sentence, and usually less useful to a PWA.

Option E

The planned window

A different page for a different event: maintenance that somebody scheduled. Named window, live countdown to the return, and what to do meanwhile. Served as a static file by whatever sits in front, so it works even when nothing else is running.

Optimises for

  • Deploys and data refreshes, where the end time is known — which converts an outage from alarming to merely inconvenient.
  • The only option that also covers the frontend itself being down.

Costs

  • Needs somewhere to put it and something to switch it on: a proxy rule, or a flag file the frontend checks.
  • Wrong and slightly insulting for an unplanned outage — it must never be the default.

Option F recommended alongside C

The degraded banner — not a page at all

For the outage this tool is uniquely able to survive. Every portfolio can be served from the bake with no database; what fails is live resolution, export and saving. So the tool opens, in read-only, with a bar saying exactly what is not available.

Optimises for

  • Getting work done during an outage instead of waiting it out — a PWA can still show a client a proposal.
  • Honesty at the point of use: the disabled control explains itself where it is, not on a page the user has left.

Costs

  • The most work of any option here: every write path needs a disabled state and a reason.
  • Read-only that is not obviously read-only is dangerous — a PWA must never believe a change was saved.

Option G shown to be rejected

The friendly apology

Big illustration, an apology, a light joke. The default of most public products, included here so the contrast is explicit rather than assumed.

Argues for itself

  • Warm, and unmistakably an error rather than a broken render.

Why not here

  • It answers none of the six questions above: not whose fault, not whether the work is safe, not when it is back, not what to report.
  • An apology to an internal colleague who has a client waiting reads as a stall.
  • The illustration occupies the space the status would.

Recommendation

Option C, with B's detail behind its disclosure, and Option E as a separate static file for planned windows. C answers the two questions that actually matter to someone with a client on the phone — is my work safe and is it back — and answers the second by simply coming back. B's diagnostics are worth having but not worth leading with; a disclosure costs nothing and keeps the page calm. E is a different event and deserves a different page, and it is the only one that survives the frontend itself being down.

F is the ambitious one and I would keep it on the list rather than in this piece of work. Serving a proposal read-only from the bake during an outage is a genuinely valuable thing for this tool specifically — but it is a change to how the page gets its data, not an error page, and it should be scoped on its own.

D I would not build as drawn, because three of its four lights have nothing to read from. The component health endpoint behind it is worth building; the board can follow it.

What I would need before building one

1
Does /health on the frontend reflect the backend?

It does not — I checked. dashboardFrontend.health() is an unconditional {'status': 'ok'}, so it reports Flask and nothing else. Option C therefore needs one of: a frontend health route that proxies the backend's, a new backend-aware probe, or polling a real API endpoint and treating 502/504 as “still down”. The last needs no server change and is what I would do first, but it costs an authenticated round trip per poll. This is the single most important dependency in this document.

2
Who does a PWA contact, and how?

A mailbox, a channel, a ticket queue? Options B and D both want a real destination; “Report to PMG Engineering” is a placeholder I invented.

3
Is a raw error string acceptable on this screen?

Internal-only says yes. If a PWA might have this on screen in front of a client, B's block goes behind the disclosure permanently and the reference becomes the only visible artefact.

4
How are planned windows announced today?

Option E needs a switch — a proxy rule, a flag file, or a config value with start and end times — and someone whose job it is to set it.

5
Is the 300s proxy timeout right?

Five minutes of a spinner before a 504 is a long time to learn nothing. If the intent is that a slow resolve can legitimately take that long, the page should say so while it waits rather than appearing hung — which is a different design job worth doing at the same time.

6
Should the page name the proposal?

C's reassurance is much stronger when it says USD Moderate Full, three columns rather than “your work”. That needs the last render cached client-side. Confirm that caching a scenario's name and shape in localStorage is acceptable.
