Since this was written

The dependency described below has been removed (D67). The workbook is now written from the payloads by the tool itself, in ~0.13 s, with four sheets rather than three — the assumptions sheet that step 6a used to throw away is kept. What follows is the trace of the path as it stood, and remains the record of why the change was worth making.

The short answer, and the surprise in it as at 3 Sept, before D67

The button posts a scenario id — nothing else. The server rebuilds the whole workbook from state it already holds, re-validating and re-resolving rather than trusting anything the page sends.

On the configuration running today that export calls the real epsilonPhi engine and takes about 24 seconds warm, 75 seconds cold — even though the same service answers a portfolio request from the baked store in 4 milliseconds. The bake does not cover exports. Section 5 is why.

Four engine touches, all under one coarse lock because the library's caches and its mutable SAAPortfolio are not demonstrably thread-safe:

with tempfile.TemporaryDirectory() as tmpdir:

The engine writes a workbook to a temp directory; the service reads it back with openpyxl, drops the assumptions sheet, appends its own Implementation sheet and returns the bytes. Any exception that is not already an AnalyticsError is wrapped as one, which the router turns into a 502.

The Implementation sheet is the tool's own work

It is the one sheet the analytics library has nothing to do with — and the one with the most dependencies of its own. buildImplementationRows (workbook.py:68) is the single Python source of those numbers, and the test suite checks it against the page's JavaScript mirror by running the extracted JS through node.

Reads

The sleeve library

sleeves.listSleeves → sleeveRepo → the SQLite store at SCENARIO_SLEEVES_DB. Auto-attached categories take their single library sleeve without a choice.

Reads

The product catalogue

Every line item's ticker, style, vehicle, source, liquidity, currency, cost and fee group comes from products.py reading SCENARIO_PRODUCTS_SOURCE.

Reads

The fee card

fees.tierFor(topAccountSize) and fees.managementFee(...) price each product from the schedule, tier, level and fee group (D51). fees.deliveryInfo() stamps the card's provenance into the sheet.

Rounding is the sheet's own rule. Weights are rounded to 2dp by largest remainder across the whole table so the column sums to exactly 100.00, and notional and weighted fee derive from that printed weight — so the workbook hand-reconciles against the screen (spec 8.4).

Fees change its shape. With fees off the sheet has 11 columns and no fee preamble; with them on, 14 — Fee group, Mgmt fee, Wtd fee (bp) — plus four preamble rows naming the schedule, level and account-size tier (D52). Measured: 11,816 bytes against 12,592.

5The thing worth acting on

The bake covers reads, not exports

The whole point of the baked store is that a cold process answers a portfolio request in milliseconds without importing the analytics library. It does: 4.2 ms. But BakedScenarioPort.build_export has no baked workbook to serve, so with the fallback on it hands the job to the live adapter — and the first export of a process pays the full engine setup the bake exists to avoid.

So the service has two very different performance characters depending on which button you press, and nothing on screen says so. The user sees columns appear instantly, presses Download Excel, and waits 25 seconds — or 75 on a service that has just restarted.

Three ways out, in ascending order of work

Cheapest

Warm the engine at start-up

Call _ensureReady() on boot when the fallback is on. Turns the 75-second first export into a 24-second one and moves the cost somewhere nobody is waiting. Does not help the steady state.

Moderate

Tell the user

The button says Preparing… with no sense of scale. A 25-second wait needs either a progress affordance or a plain warning. Cheap, and it is the difference between slow and broken-feeling.

The real fix

Decide what the export is for

If Reporting's two sheets must be the engine's own output, 24 seconds is the price and it should be made visible. If they need only match it, writeFixturesWorkbook already produces all three sheets in 63 ms — and the question becomes whether its Portfolios and Risk Dashboard are close enough to ship.

6Smaller things found while tracing

The export bypasses the service-health layer

exportWorkbook() calls fetch directly, not apiFetch — so a failed export never reaches App.noteService() and cannot mark the service down. The button is gated by canExport() but does not feed it. A one-line change if that asymmetry matters.

The 300-second proxy timeout is the ceiling

Not a configuration knob on the export itself. A four-column proposal in a cold process is the case to watch: the first column resolve alone can take minutes on the live adapter, and the export's own budget sits inside the same 300 seconds.

Exports serialise

One coarse lock guards the engine, so two people exporting at once queue rather than overlap. Correct, given the library's thread-safety, but it means the second person waits 50 seconds, not 25.

The server re-does the client's work deliberately

Every gate the page applies is re-enforced, and every column is re-resolved. The body of the POST is empty by design — the scenario on disk is the only input, so a stale or tampered page cannot change what is exported.

The fee level has a vocabulary

Six values: Management or PMG, each × Floor / Target / Ceiling. Plain Target is rejected — worth knowing when scripting against the API.

The workbook is built twice on the engine path

Reporting writes to a temp directory, then openpyxl reopens it, edits it and re-serialises to a buffer. Unavoidable while Reporting's only output is a file, but it is two full workbook serialisations per download.
