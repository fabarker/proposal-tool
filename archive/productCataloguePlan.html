Proposal Tool · design note

Product Catalogue

A view-only window onto the delivered product table for admins: browse, search, filter and sort every product the sleeve repository can select from, see where each one is used, and see where the table came from — without a way to change any of it.

2 September 2026Status: built 2 September 2026, as specified belowRecorded as D58 in DEVIATIONS.md

What is being asked

  • A PMG product catalogue in the UI — the whole table, not just the slice a picker shows.
  • View only. The catalogue is delivered (D56); it changes by delivery, never through the app. Nothing here writes.
  • Admin only. The same role that maintains sleeves; nobody else sees the entry.

Where things stand today

Since D56 the products live in a one-table extract — 73 rows, eleven columns, ProductId the key — read by products.py and joined into sleeves when they are served. The only place an admin currently sees products is the picker inside the sleeve editor, and a picker is built to answer one question ("which product goes here?") rather than the ones a catalogue answers: what do we have, what does it cost, which fee group is it in, where is it already used, and is this the delivery we think it is.

Two facts shape the design. The console already fetches the whole catalogue and every sleeve in one call (GET /scenario/repository), so "where is this product used" is a join the page can do for free. And the attribute columns are closed vocabularies in practice — five vehicles, two styles, two sources, four liquidities, four exposure currencies, five fee groups in the stand-in — so the filters can be derived from the data rather than hardcoded, the way every other selector in the tool is (spec 4.3).

Design

1 · Where it lives: a second view of the admin console

Not a new overlay. The Sleeve Repository console gains a view switch in its header — Sleeves · Catalogue — and the catalogue is the second view: same fetch, same admin gate, same dialog chrome, same Escape and focus behaviour. Deep links #repository and #catalogue; the admin entry links on the landing page and in the rail's brand block become two, Sleeve repository and Product catalogue, both hidden unless capabilities.canAdmin. The implementation-type control belongs to the sleeve view only: a catalogue is type-independent, so on the catalogue view that space carries the toolbar instead.

2 · The table

A catalogue is a table, so it is shown as one — the same reading as the implementation table, at the same 13px, digits tabular and right-aligned:

ColumnWhat it shows
ProductName on one line, ticker and asset class beneath it in the condensed face. The sticky first column when the table scrolls sideways.
Style · Vehicle · Source · Liquidity · ExposureThe attribute columns as the implementation table shows them.
Cost %ProductCost, two places.
Fee groupAs a pill, the same treatment the picker gives it.
Used inHow many sleeves hold the product, across every implementation type. 0 is amber: a product delivered but not yet placed anywhere is exactly what an admin building sleeves wants to find.

Every column sorts on click; the default order is the delivery's own, since the team that authored the extract grouped it deliberately. The toolbar carries a search box (name, ticker, asset class, vehicle, source, fee group — the same fields the picker matches) and one filter chip per attribute vocabulary, each listing the values found in the data with counts; a chip in force is shown filled. A three-way toggle narrows to placed / not yet placed / all. The count on the right always says what is showing out of what exists.

3 · The detail drawer

Selecting a row opens a drawer on the right rather than a modal on the modal: every field laid out in full, then Used in — one entry per sleeve holding the product, as type · category · sleeve · weight, each with Open, which switches to the sleeve view with that sleeve selected. That cross-link is the point of putting the catalogue inside the console: an admin goes from "what is this product" to "fix the sleeve it is in" without leaving. A View fee card action opens the existing card viewer (D55) pivoted to the product's fee group, because the rate is the one thing about a product that lives elsewhere.

4 · Provenance and honesty

The footer names the catalogue file, its modified time and its row count — the same line the sleeve view carries — and the legend states what the fee card's does: the catalogue is delivered and read only; it changes by delivery, not here. A stand-in catalogue (the packaged one) is flagged as such, the way placeholder fee rates are.

One warning belongs at the top of this view because this is where it is answerable. If a sleeve references a product the catalogue no longer carries — a new delivery dropped it — that sleeve is broken and withheld from the pickers (D57). The catalogue view lists those orphaned references in a notice: 2 products referenced by sleeves are not in this catalogue, naming them and the sleeves they break, with Open to each. The server derives the list (a small orphanProducts() in the repository, also added to sleeveTools --census), so the console and the command line agree.

Behaviour and rules

RuleWhereNote
Nothing writesEverywhereNo input takes a value that is sent anywhere. The API stays GET for the catalogue; the three repository writes touch sleeves only.
Admin onlyrequireAdmin on the fetch; canAdmin for the entryAs asked. Because the view writes nothing, opening it to editors later is a one-line change of gate, if wanted.
Filters are derived from the dataConsoleEach chip lists the values present, with counts. A vocabulary the delivery adds appears without a code change (spec 4.3).
Used-in is a client joinConsoleProducts × sleeves from the one fetch; no new endpoint. Counts and the drawer list agree by construction.
Orphans are server-derivedsleeveRepo.orphanProducts(), in the payload and in --censusThe console and the command line must not disagree about what is broken.
Default order is the delivery'sConsoleSorting any column is one click; sorting back is another. The file's own order is a fact about the delivery worth being able to see.
The view survives a save on the other viewConsoleSaving a sleeve updates the in-memory sleeve list the join reads, so Used-in is current without a refetch.

API

No new route. GET /scenario/repository already returns products and catalogue; it gains one field, orphans — [{productId, sleeves: [{id, variant, category, name}]}]. The fee card viewer's existing fetch serves the drawer's action.

Decisions I would make, and the ones that are yours

1
Inside the console, as a second view.

One fetch, one gate, one dialog, and the cross-link from a product to the sleeve that holds it is the feature. A separate overlay would duplicate the chrome and lose that link. Recommended: second view.

2
Admin only, as asked.

A read-only catalogue would be safe for editors too, and a PWA choosing a sleeve might well want to see what is in it. Not proposed here; noted because the gate is one line if that changes. Assumed: admin only.

3
Delivery order by default, every column sortable.

Name A–Z is the obvious alternative and is one click away. Recommended: delivery order.

4
Rates stay in the fee card.

A product's management fee depends on the schedule, the account-size tier and the level, none of which a catalogue knows. The drawer links to the card at the product's group rather than guessing a rate. Recommended: link, don't show.

5
No download.

A Download CSV of the catalogue is read-only and cheap, but the delivery already exists as a file where it was delivered; adding a second copy that leaves the app is a choice about data handling rather than UI. Left out unless wanted.

Data caveat, unchanged. The stand-in catalogue is the 73 products the authored sleeve library carried, with slug ids and rule-of-thumb fee groups. The view shows whatever the delivery says; it does not make it true.
