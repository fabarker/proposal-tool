# Kickoff prompt

Paste the block below as the first instruction to whoever — or whatever — is doing the build.
It is deliberately short: it points at the package rather than restating it, because the package
is the specification and a paraphrase would compete with it.

---

```
Build the Epsilon Phi Proposal Tool, front end and back end, working end to end.

WHERE
  Repo:    /Users/francisbarker/repo/epsilon-psi
  Package: epsilon-phi-core/proposal-tool/     <- everything you need is here
  You build and run it inside epsilon-phi. You write the back end exactly as it
  would have to be written inside isg-cyrus-pmg/src/cyrus_pmg, because this gets
  transplanted there. epsilon-phi is where you develop it; Cyrus is what you are

BEFORE YOU WRITE ANY CODE
  Read, in this order, and do not skim:
```

## Why it is shaped this way

**It points, it does not restate.** The package is 785 lines of host audit, a 16-section spec and
47 decision entries. A prompt that summarises them creates a second, worse source of truth that
will drift. The only things restated here are the ones that change behaviour if missed.

**Reading order is an instruction, not a suggestion.** The most expensive failure available is
starting to code against a spec that has already decided the thing being invented.

**Step zero exists because phase 3 dies without it.** epsilonPhi needs `CAppConfig.setup()` and a
database. Discovering that in week three is worse than discovering it in hour one, and phases 1
and 2 genuinely do not need it.

**The gates are phrased as observable facts**, not activities — *"/api returns a well-formed 502
when the service is down"* rather than *"build the proxy"*. A gate you can be wrong about is not a
gate.

**"Do not stall" is explicit**, because independence and a spec that claims completeness pull in
opposite directions the moment a real gap appears. The instruction is: decide, record, continue.

**The last line asks for a plan first.** It is the cheapest possible check that the reading
actually happened.
