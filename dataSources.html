Proposal Tool · provenance review

Where every number in the service comes from

A walk through epsilon-phi-core/proposal-tool naming the origin of every dataset the running service reads — portfolios and weights, analytics, products, sleeves, fees, and the several smaller sets that are easy to forget. For each one: the file or store it is read from, the environment variable that repoints it, whether the contents are real or a stand-in, and what production is expected to put in its place.

Reviewed 3 September 2026 Adapter in force baked Scope proposal-tool/ in full Method every open(), load_workbook, connect and getenv in the package

The shape of it

Nothing in this repository holds market data. No price, no return series, no covariance. Every risk and return figure the tool shows is produced by the epsilonPhi analytics library, which brings its own data version. Everything else divides cleanly into four tiers.

1

Stand-in extracts

Flat files in the repo standing in for databases owned downstream. Each is repointed by one environment variable. Five of them.

2

Stores the tool owns

Data the Proposal Tool itself writes and is the authority for. Three: the sleeve database, the scenario store, the baked analytics store.

3

Constants in code

Numbers that are policy or model decisions, living in .py files rather than any database. Easy to overlook, and the least governed.

4

The analytics library

epsilonPhi, resolved lazily through one seam. The only source of return, risk, stress and VaR — and the only place market data enters.

Tier 1 — the stand-in extracts

These five files are the seam with systems the Proposal Tool does not own. Each was authored to the exact shape the supplying system is expected to hand over, so that swapping in the real thing is a change of path, not of code.

Strategic portfolios and weights

weights inventedtickers real
saaSource/saaPortfolios.csv→universe.py→saaKeys.py (name parse)→PortfolioKey→weightMap()→the adapter
File
proposal-tool/saaSource/saaPortfolios.csv — and the same rows as saaPortfolios.xlsx, for diffing in review.
Shape
Three columns: PortfolioName, AssetTicker, Weight. One row per holding. 172 portfolios across 2,468 rows.
Override
SCENARIO_SAA_SOURCE (CSV or XLSX).
The key
The portfolio name is the only key, and it carries currency, risk level and allocation type. saaKeys.py matches longest-token-first against closed vocabularies — 72 of the 172 names cannot be split on whitespace. Hedging is not in the name; it joins the key only when the analytics run.
Real?
The weights are fictitious. The tickers are the real ones the tool carries. The allocations across them were generated by buildSaaSource.py to be plausible and internally consistent. Nothing from this file reaches a client.
Production
The downstream SAA database, exporting the same three columns. The parse runs offline in the bake, never at request time, so a rename is caught before it can reach a user.

Where the weight model originally came from. Before deviation D54, portfolios were constructed in portfolio_weights.py from four product-level anchors — Low Volatility, Conservative, Moderate, Aggressive — transcribed by hand into _ANCHOR_INPUTS from Core Portfolios.xlsx, with the intermediate risk levels interpolated and All Equity extrapolated. That workbook is in this repository, but outside the Proposal Tool: src/Scripts/Case Studies/1. Portfolio Analysis/Core Portfolios.xlsx. The construction code still exists and still runs as a CLI, but the service no longer uses it for weights — the extract does.

Products

stub data
productSource/products.csv→scenario/products.py (validating reader)→sleeve repository + product catalogue
File
proposal-tool/productSource/products.csv, with products.xlsx alongside so the workbook path of the reader is exercised too.
Shape
73 products, thirteen columns — one row per product, one column per field: ProductId, Name, Ticker, AssetClass, Style, Vehicle, Source, Liquidity, ExposureCurrency, ProductCost, FeeGroup, DistributionYield, MinimumInvestment.
Override
SCENARIO_PRODUCTS_SOURCE (CSV or XLSX).
Validation
The reader refuses an extract with a missing column, a duplicate id, an empty name, a non-numeric cost, a negative figure, or a fee group the fee card does not price. The last of those ties this file to feeRates.csv.
Real?
The products are the ones the authored sleeve library carried. The ids are slugs of the names — a real catalogue brings its own. DistributionYield and MinimumInvestment are placeholders throughout. 38 of the 73 have no ticker at all, by design: the SMAs and the private-market programmes do not have one.
Production
The product database, exported as the same one-table extract.

Fee rates and the fee card

placeholder — and says so
scenario/feeRates.csv (the rates)+scenario/fees.json (the structure)→scenario/fees.py→schema→fee card
Rates
scenario/feeRates.csv — one row per cell, 180 cells: schedule, feeGroup, tier, tierMin, tierMax, source, point, rate. Two schedules (CASP, RDR), two sources (Management, PMG), three points (Floor, Target, Ceiling).
Structure
scenario/fees.json — the schedule list and their order, which schedules price by fee group, the default level, the points, and the delivery stamp. A row cannot supply ordering, so it lives here.
Override
SCENARIO_FEES_SOURCE repoints the rates. The structure file is not overridable; it is edited when the real card arrives.
Real?
No. The card declares itself: placeholder: true, version 0.0-placeholder, source "placeholder card generated in-repo, not a delivery". That stamp travels into the schema, into the export, and into the bake manifest, so no consumer can mistake it for a delivered card.
Production
The delivered fee card in the same long-CSV shape, with fees.json updated to its schedules and stamped with its real version and as-of date.

Advisor directory

stub data
File
scenario/advisors.xlsx, sitting beside the module that reads it. One sheet, two columns — name, office — 24 rows.
Read by
scenario/advisors.py, loaded once and cached. Search returns nothing below two characters, mirroring the UI hint rather than dumping the directory.
Override
None. The path is fixed to the module directory. This is the only tier-1 extract with no environment override.
Production
The Primary PWA table, swapped in behind the same two functions. Excel-backed here is deliberate — spec 4.2 item 7.

Sleeve seed

real namesstub contents
File
proposal-tool/sleeveSource/sleeves.csv — Variant, Category, Sleeve, ProductId, Weight. 102 sleeves across 260 rows, plus sleeves.xlsx.
Override
SCENARIO_SLEEVES_SEED.
Validation
buildSleeveSource.py checks every product against the catalogue, refuses a product listed twice in one sleeve, and requires weights to sum to 1.
Real?
The sleeve names are PMG's own, supplied for each category. The products inside them and their weights are placeholders.
Important
This file is a seed, not a source. It is read exactly once, when the database is empty. See finding F1.

Tier 2 — the stores the tool owns

Baked portfolio analytics

computeda frozen snapshot
saaPortfolios.csv→bake.py→epsilonPhi→service/var/baked/{ccy}_{hedging}.json + manifest.json→bakedAdapter

This is what the service is serving right now. The store answers a portfolio request from disk without importing the analytics library at all — roughly 3 ms cold.

Location
service/var/baked/ — 16 slice files (one per currency × hedging policy), 688 payloads, 2.8 MB, plus manifest.json.
Override
SCENARIO_BAKED_DIR; SCENARIO_BAKED_FALLBACK=1 lets a miss fall through to live analytics.
Built
2 September 2026, 15:34:35 — from saaPortfolios.csv as modified that morning at 10:59. Both facts are recorded in the manifest, along with the fee card stamp, the derived facets, and the parse result (172 portfolios, 2,468 holdings, 0 unparsed, no unknown tickers).
Currencies
USD, GBP, CHF, EUR × four hedging policies. GBP, CHF and EUR were analysed in a USD context and the manifest records it as currencySubstitutions; each payload is stamped with its analyticsCurrency. See finding F4.
What is in a payload
Category rows, three headline metrics (estimated return, volatility, Sharpe), factor stress tests by period, and the VaR / CVaR / probability-of-loss block at 99% confidence across the horizon set.

the authority
Location

Override
SCENARIO_SLEEVES_DB.
Contents now
101 sleeves, 258 product rows. meta records the seed: seededAt 2026-09-02T17:47:03, seededFrom …/sleeveSource/sleeves.csv.

Scenario state

user-created
Location
SCENARIO_STORE_DIR, defaulting to {tmpdir}/pmg_proposal_scenarios. One JSON file per scenario, written atomically via a temp file and rename.
Contents
The mandate and basis a user entered — nothing sourced from anywhere else. Expires untouched after SCENARIO_RETENTION_HOURS (24 by default).
Note
The default lands in the system temp directory, so a reboot or a temp sweep drops in-flight scenarios. Set the variable for anything but development.

Tier 3 — data that lives in code

These are the numbers with no file and no database behind them. They were chosen, not derived, and they are the least visible part of the data estate — which is exactly why they are worth listing.

Asset universe — portfolio_weights.ASSET_METADATA

19 assets as (ticker, reporting name, category), in the supplied table's order. It is the authority for three things at once: which tickers exist, what they are called on screen, and which of the seven categories each belongs to. The zero-padding that gives every portfolio an identical asset set is driven off it.

Hedge ratios — HEDGE_RATIOS_BY_OPTION

Four policies: Hedged, Unhedged, Equity Not Hedged, ISG Hedged. Recorded as deviation D3. Assumed, not delivered.

Analytics context — CONTEXT_START_DATE / CONTEXT_END_DATE

30-Nov-1983 to 31-Dec-2022. Every figure the tool reports is estimated over this window, and it is reported alongside the library's DATAVERSION.

Construction rules — scenario/rules.py

Mandate floor $5m; private-assets minimum $20m; at most four portfolios; the tactical tilt at 8% into LHUT1T3; the strategic volatility premium at 7.5%, offered in USD and GBP only; risk-level labels; which implementation types exclude real estate. All policy.

Sleeve grouping — SLEEVE_GROUPS

Private Equity and Other Private Assets are one group with one sleeve and one selector. A genuine PMG rule, expressed as data on the schema so the UI reads it rather than hard-coding it.

Fixtures analytics — fixturesAdapter.py

Per-category coefficients that synthesise return, risk and stress deterministically from the weights. The weights and availability are the real universe; only the numbers are invented. Permanent by design (spec 4.4), and the only way to reach every error and timeout state.

Tier 4 — the analytics library

Every risk and return number the tool shows originates outside this repository. scenario/engine.py is the single seam: a lazy resolver over six symbols, with the root package read from SAA_ENGINE_PACKAGE (default epsilonPhi), so a rename or a layout change in the host library is a one-line edit rather than a search.

SymbolModuleWhat the tool takes from it
SAAPortfoliocore.portfolio.SAAPortfolioThe portfolio object. Return, risk, Sharpe, factor stress tests and the VaR policy are all read off it directly — never off the reporting table builders, which exist to lay out a workbook.
ContextCreatorcore.schema.SchemaThe estimation context over the configured date window.
AssetReturnEstimatorcore.estimator.assetReturnEstimatorThe return estimates behind every figure.
Reportingcore.reporting.ReportingThe Excel export — portfolios and risk sheets.
DATAVERSIONcore.env.EnvStamped onto results so a number can be traced to the data behind it.
CAppConfigcore.config.appConfigLibrary configuration.

The library is not thread-safe in the way the service needs, so live resolution runs under a lock and the results are memoised per basis and key.

Findings worth your attention

F1
The sleeve database has drifted from its seed file.

The database holds 101 sleeves / 258 rows; sleeveSource/sleeves.csv holds 102 / 260. The seed is read once, when the database is empty — it was read at 17:47 on 2 September, and the CSV was edited at 19:17 that evening. The database is the runtime authority and is correct; the CSV is now a stale snapshot of it. Either re-export the CSV from the database, or treat it purely as a first-run seed and stop reading it as documentation.

F2
The fee card is a placeholder, and everything downstream knows it.

fees.json carries placeholder: true and version 0.0-placeholder, and that stamp reaches the schema, the export and the bake manifest. This is working as intended — but it does mean every fee figure currently on screen is invented, and the real card is a genuine dependency before anything client-facing.

F3
The baked store is a snapshot with no staleness check at request time.

It records the SAA extract's path and modification time, so drift is detectable — but nothing detects it automatically. Change saaPortfolios.csv and the service keeps serving the old analytics until someone rebakes. A start-up comparison of the recorded source.modified against the file on disk would turn a silent problem into a loud one.

F4
Non-USD portfolios in the baked store carry USD-context analytics.

GBP, CHF and EUR were baked with the analytics context forced to USD; the portfolio keeps its own currency in its tag. The manifest records this as currencySubstitutions and each payload is stamped with its analyticsCurrency, so it is honest and traceable — but the numbers under a GBP tag are not GBP-context numbers, and that has to be understood before anyone reads them as such.

F5
Under the baked adapter, exports may not come from the analytics library.

If a live delegate is available the export is built by Reporting. If it is not, build_export falls back to the fixtures workbook writer — a real file, but not the library's output. SCENARIO_BAKED_FALLBACK is on by default, so today the delegate exists; the fallback path is worth knowing about before it is relied on.

F6
Both access lists default to a single developer.

PMG_ALLOWED_KERBEROS and PMG_ADMIN_KERBEROS both default to fbarker, and identity comes from a kerberos cookie set by the /_dev_login stub standing in for GSSSO. Correct for development; both are deployment inputs, not data the tool owns.

F7
The advisor workbook has no environment override.

Every other extract can be repointed without a code change. advisors.xlsx is pinned to the module directory, so pointing it at a real directory means editing advisors.py. A SCENARIO_ADVISORS_SOURCE variable would make the set uniform.

F8
The scenario store defaults into the system temp directory.

Fine for development, lossy anywhere else. SCENARIO_STORE_DIR should be set explicitly in any deployed environment.

What a production cutover actually needs

DatasetHow it is swappedAnything more than a path change?
Strategic portfoliosPoint SCENARIO_SAA_SOURCE at the real extract, rebake.The name vocabularies in saaKeys.py are closed — any name the real database uses that is not in them is rejected, deliberately, at bake time.
ProductsPoint SCENARIO_PRODUCTS_SOURCE at the real extract.Every FeeGroup must be priced by the fee card, and sleeves reference products by ProductId — new ids mean the sleeve library is rebuilt against them.
Fee cardPoint SCENARIO_FEES_SOURCE at the delivery.Yes — fees.json must be edited to the real schedules and stamped, and the placeholder flag cleared.
AdvisorsReplace the workbook read with a table read.Yes — a small code change, or add the missing override first (F7).
SleevesNothing. The database is the tool's own.Contents need filling with real products; the names are already PMG's.
AnalyticsNothing, if the host installs epsilonPhi. Otherwise set SAA_ENGINE_PACKAGE.Rebake once the real extract is in, and re-check the currency substitutions (F4).
Rules & assumptionsEdit rules.py and portfolio_weights.py.Yes — these need sign-off rather than a swap. They are the only datasets with no owning system.

What is not in the picture

  • No market data of any kind lives in this repository — no prices, returns, covariances or factor histories. All of it is inside the analytics library, at its own DATAVERSION.
  • No client data. The only thing a user contributes is the mandate and basis they type, and that lives in the scenario store for 24 hours.
  • No realised fund metrics. The product catalogue deliberately carries none — no return, volatility or drawdown. Cost, distribution yield and minimum investment are the only figures, and the last two are placeholders.
  • Core Portfolios.xlsx is not read by the service. Its four anchor columns were transcribed into _ANCHOR_INPUTS once. The workbook itself sits outside the Proposal Tool, in src/Scripts/Case Studies/.
