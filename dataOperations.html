Proposal Tool · data operating model

Managing the data that feeds the service

1The four questions every dataset must answer

The framework is small on purpose. A dataset is under control when all four have a named answer; anything without one is where the next incident comes from.

Question one

Who owns it?

A named team that can be asked "is this right?" and answer. Not the team that stores it — the team accountable for its content.

Question two

How often does it change?

A cadence, or an explicit "on delivery, unpredictably". This decides whether you poll, subscribe, or wait to be told.

Question three

What must pass before it counts?

A gate that can fail. If a bad version of this dataset cannot be automatically rejected, it is not controlled — it is merely watched.

Question four

How do you undo it?

A rollback that has been performed at least once, not one that is theoretically available.

The organising fact

The Proposal Tool owns almost none of its data. It owns the sleeve library and the scenarios users create. Everything else is somebody else's data, borrowed — which means the operating model is mostly about receiving well, not about editing well.

2Classification — what decides the process

Two questions sort every dataset into one of four classes, and the class determines everything that follows: the gate, the release path, the blast radius and the rollback.

Axis one

Who changes it?

An outside team delivering a file · an admin working inside the app · a developer editing code.

Axis two

Does it invalidate the bake?

688 precomputed payloads sit between the source data and the screen. Some changes make them wrong; most do not. This is the single biggest operational distinction in the system.

A

Rebake-triggering

Datasets

SAA extract · analytics library version · hedge ratios · context window

Blast radius

Every number on every screen. A change here silently invalidates all 688 baked payloads.

Release path

Census → bake to a new directory → verify → swap. Never in place.

B

Delivered, live-read

Datasets

Fee card · products · advisor directory

Blast radius

Presentation and implementation, not analytics. No rebake needed.

Release path

Diff against what is live → accept → restart → verify. Products alone reload on their own.

C

Tool-owned, continuous

Datasets

Sleeve library · scenario state

Blast radius

What an adviser can select. Changes take effect immediately, with no release at all.

Release path

None — admins edit in-app. Governed by who is an admin, by a periodic census, and by a history that keeps every version.

D

Policy constants

Datasets

Mandate floors · tilt % · volatility premium · risk labels · sleeve grouping

Blast radius

What the tool will let a user do, and what it recommends. The highest-consequence, lowest-visibility data in the estate.

Release path

Code change, tests, review, deploy. Needs sign-off, not a swap.

The class-D problem

Class D has no owning system and no delivery. A $5m mandate floor, an 8% tactical tilt and a 7.5% volatility premium are business decisions living as Python constants. They are the only datasets where "who approved this number, and when?" currently has no answer outside the git log. Give class D a named approver and an annual review — that is the single highest-value governance change available here.

3The pipeline: one road in

Every delivered dataset (classes A and B) should travel the same six stages. The value is that each stage can fail, and failing early is cheap. The repository already implements this end to end for the fee card; the others implement part of it.

Stage 1

Land

The delivery arrives as a file, in a known place, untouched. Never edited by hand.

Stage 2 · gate

Census

What does this file contain? Counts, coverage, anything unparseable. Read-only.

Stage 3 · gate

Diff

What changed against what is live? Cell by cell. This is the stage that catches a bad delivery.

Stage 4

Accept

Copy into place and stamp the provenance — version, source, as-of. The only sanctioned way in.

Stage 5

Rebuild

Class A only: rebake into a new directory, then swap. Class B: restart.

Stage 6 · gate

Verify

Tests, censuses, and the provenance line on screen. Only now is the change real.

The fee card is the pattern to copy

feeTools does the whole road: --census says what a file holds, --diff reports "these eleven cells moved" before anything is touched, and --accept refuses a card the framework cannot price from — a gap, disagreeing tier edges, a crossed band — so a bad delivery fails at the desk rather than at the next service start. Every other delivered dataset should be brought up to this standard. The two missing are products and advisors.

5Dependencies and order of operations

Three datasets have hard dependencies on each other. Updating them out of order produces failures that look like unrelated bugs, so the order is not a preference.

Fee card→Products→Sleeves Every product's FeeGroup must be priced by the card, and every sleeve references products by ProductId.
SAA extract→bake→baked store→every figure on screen Plus the analytics library and the class-A constants, which feed the bake directly.
Asset metadata→SAA extract The 19 tickers are a closed set; an extract naming anything else is rejected at census.

The three failure modes this prevents

  • A new product with an unpriced fee group. The catalogue reader refuses the whole file, so the product catalogue and sleeve repository both fail — not just the new product. Update the fee card first.
  • A product dropped from the catalogue while sleeves still reference it. Sleeves become broken and the failure surfaces to advisers, not to you. Run sleeveTools --census immediately after any product update — it reports exactly this as orphaned products.
  • A renamed portfolio in the SAA extract. The name is the only key, and the vocabularies are closed, so the name is rejected rather than guessed. Run bake --census before baking; it lists every name that did not parse and exits without writing anything.

6Runbooks

The actual commands, from proposal-tool/service with PYTHONPATH=. set. These are the tools that exist today; where one does not exist, the runbook says so rather than pretending.

A. New fee card delivered

class Bfully tooled
  1. Land it unedited

    Put the delivered CSV somewhere outside the package. Do not open it in Excel and re-save — that is how a long CSV acquires a changed encoding or a lost leading zero.

  2. Census, then diff 
    PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.feeTools --census
PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.feeTools --diff /path/new.csv

    The diff prints every moved cell with its before, after and delta, plus anything added or removed. This is the review. Send it to the pricing desk and get the changes confirmed before going further.

  3. Take your own backup first 
    # accept overwrites feeRates.csv in place and keeps no copy
cp cyrus_pmg/pmgService/scenario/feeRates.csv \
   ~/fee-backups/feeRates.$(date +%Y%m%d).csv

    See gap G4 — this step should not be manual, but until it is automated, it is the only rollback you have.

  4. Accept with the real provenance 
    PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.feeTools \
    --accept /path/new.csv --version 2026.3 \
    --source "PMG pricing desk" --as-of 2026-09-01

    Accept refuses a card the framework cannot price from, so a bad delivery fails here. On success it stamps version, source and asOf into fees.json and clears the placeholder flag.

  5. Restart and verify

    The delivery is read at import, so a restart is required. Then re-run --census and confirm the version and as-of date are the ones you accepted, and that the app no longer reports a placeholder card.

B. New SAA extract

class Arebake required
  1. Census the extract before trusting it 
    SCENARIO_SAA_SOURCE=/path/new.csv PYTHONPATH=. \
  python3 -m cyrus_pmg.pmgService.scenario.bake --census

    Enumerate only — it reports the source, the derived facets and every name that did not parse, then exits. Zero unparsed names and zero unknown tickers is the pass condition. Anything else is a conversation with the SAA team, not a fix on your side.

  2. Bake into a new directory — never over the live one 
    SCENARIO_SAA_SOURCE=/path/new.csv PYTHONPATH=. \
  python3 -m cyrus_pmg.pmgService.scenario.bake \
    --all --workers 4 --out var/baked.new \
    --analytics-currency USD

    Roughly 688 payloads across 16 slices. The bake resumes by default, so an interruption is recoverable — but note that the authoritative manifest is written by the parent process after all workers finish. If a run is interrupted, the slice files on disk are the truth and the manifest under-counts; simply re-run to repair it.

    Drop --analytics-currency once the library carries native configs for GBP, CHF and EUR — see decision D2.

  3. Verify the new store before it is live

    Check the manifest: portfolios baked, currencies, the recorded source path and modification time, zero unparsed. Spot-check two or three portfolios against the previous store and satisfy yourself the movements are explicable.

  4. Swap, keeping the old one 
    mv var/baked var/baked.bak && mv var/baked.new var/baked
./stop_dashboard.sh && ./start_dashboard.sh

    The previous store stays as var/baked.bak. That is the rollback, and it is a directory rename — seconds, not a rebuild.

  5. Confirm on screen

    The app reports its own provenance: adapter, data version, portfolios baked, currencies and the bake date. If that line does not show what you just built, the service is serving the old store.

C. New product extract

class Bpartly tooled
  1. Validate before swapping 
    SCENARIO_PRODUCTS_SOURCE=/path/new.csv PYTHONPATH=. \
  python3 -m cyrus_pmg.pmgService.scenario.sleeveTools --census

    Pointing the census at the candidate catalogue is the closest thing to a dry run available today. It reads the new file through the validating reader and reports every sleeve that would break and every product the sleeves reference that the new catalogue no longer carries. Do this before the file goes into place, not after.

  2. Check the fee groups are priced

    The reader rejects the entire catalogue if any row carries a fee group the fee card does not price. If the delivery introduces a new group, the fee card update has to land first (see runbook A).

  3. Swap the file

    Products are cached on path and modification time, so the service picks up a changed file on its own — no restart. This is convenient and it is also a risk: a product change can go live without anyone deciding it should. Treat the file itself as the control point.

  4. Re-census and repair

    Run sleeveTools --census again against the live store. Any orphaned products must be resolved by an admin editing the affected sleeves before an adviser meets them.

D. Sleeve library

class Cfully tooled
  1. Day to day: in the app

    Admins create, copy, remove and re-apply sleeves in the sleeve repository. There is no release and no operator involvement. The control is who holds PMG_ADMIN_KERBEROS — and, since D65, a record that makes every change reversible.

  2. Every version is kept, and a delete is recoverable 
    PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.sleeveTools --history 42
PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.sleeveTools --archived
PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.sleeveTools --activity 40

    Every write appends a revision holding the whole sleeve, with who did it and when. Archiving takes a sleeve out of the library, not off the record. An admin mistake no longer needs you: the console's History drawer puts any earlier version back, its Archive tab restores archived sleeves singly or as a batch, and its Activity tab shows every change across the library newest first (D66). Escalation is for a mistake nobody noticed until the whole library moved on.

  3. Health check on a schedule 
    PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.sleeveTools --census

    Reports what the store and catalogue hold, every broken sleeve and why, every orphaned product, and any fixed category not holding exactly one sleeve. Run it weekly.

  4. Promotion between environments, and backup 
    # take a dated export — this is your sleeve backup
PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.sleeveTools \
    --export ~/sleeve-backups/sleeves.$(date +%Y%m%d).csv

# load into another environment through the same validation a save gets
PYTHONPATH=. python3 -m cyrus_pmg.pmgService.scenario.sleeveTools \
    --import sleeves.20260903.csv --replace

    Same-named sleeves are overwritten; --replace clears the store first; a single failing sleeve aborts the whole load. The export is the only backup of a class-C dataset, so schedule it.

  5. Retire the seed file

    sleeveSource/sleeves.csv is read once, when the database is empty, and it has already drifted from the live store. Either re-export over it after any significant change, or delete it and keep dated exports instead. Do not read it as documentation of what the tool holds.

E. Advisor directory

class Bnot tooled
  1. Today: replace the workbook and restart

    advisors.xlsx sits inside the package with no environment override and no census. Replace it, restart, and search for two or three known names to confirm.

  2. Fix the shape first

    This is the least controlled dataset in the estate — a hand copy into a package directory with no validation and no provenance. Gap G2 makes it match the others; do that before the directory becomes a live dependency.

F. Policy constants

class D
  1. Treat the change as a data change, not a code change

    Raising the mandate floor or moving the tactical tilt is a business decision that happens to be expressed in Python. Record who asked, who approved and why, in the commit message — that is the only audit trail these have.

  2. Run the suite 
    cd proposal-tool/service && PYTHONPATH=. python3 -m pytest tests -q
# expected: 193 passed, 4 skipped

    The suite covers the rules, the sleeve repository, the baked adapter and the Python/JavaScript mirror pairs. A green run is the gate.

  3. Rebake if the constant is class A

    Hedge ratios and the context window feed the analytics. Changing them without rebaking leaves the store describing a model that no longer exists.

Why the last check matters most

Every other check inspects a file. This one inspects what a user would actually see. Most data incidents in a system like this are not corrupt data — they are correct data that never reached the running process, because a restart was missed or a directory was not swapped. The provenance line catches exactly that class of failure and nothing else does.

Symptom → likely cause

Numbers changed and nobody expected it

A rebake ran, or the analytics library moved data version under you. Check the manifest date and the provenance line first, before looking at any weights.

The product catalogue is empty or erroring

The whole extract was rejected — almost always one bad row: a duplicate id, an empty name, a non-numeric cost, or a fee group the card does not price. The reader is all-or-nothing by design.

A sleeve shows missing products

A product extract dropped an id a sleeve still references. sleeveTools --census names it exactly. An admin repairs the sleeve; no release needed.

A sleeve changed and nobody knows why

It does know. The console's Activity tab, filtered to the sleeve or the person, or sleeveTools --history <id>, gives every version with who saved it, when, and what moved. Put any of them back in one click.

Portfolios missing after an extract update

Names that did not parse were rejected, not guessed. bake --census lists them. This is the closed vocabulary working as intended.

Fees look wrong across the board

Check whether the card still reports itself as a placeholder. Until a real card is accepted, every fee figure on screen is invented.

A change was made but nothing moved

The service was not restarted. Only products self-reload; the fee card, the advisor directory and the SAA universe are all read once at import.

9Operating rhythm

Weekly
The console's Activity tab on Last 7 days — the only class-C dataset with no release gate, so a periodic look is the control, and the feed is that look in thirty seconds. sleeveTools --census for the structural checks. Take a dated sleeve export and a copy of the .db at the same time.
Monthly
Product extract refresh, followed by a census. Confirm the fee card's version is still the one you expect. Review who is on the two access lists.
Quarterly
SAA extract refresh and full rebake, on the supplying database's schedule. Full verification checklist. Confirm the analytics library's data version has not moved without notice.
Annually
Class D review: mandate floor, private-assets minimum, tactical tilt, volatility premium, hedge ratios, context window. Each one re-approved or changed, with the decision recorded.
On delivery
Fee card — unpredictable, a few times a year. Runbook A, in full, every time.
On demand
Sleeve changes by admins, continuously. No involvement needed, by design.

11What you need to decide

Decision 1

Who owns each dataset?

The ownership map has a column deliberately left blank. Until a named team sits in it for the fee card, the products, the advisor directory and the SAA extract, every runbook here has an unresolved dependency at its first step.

Decision 2

Do non-USD portfolios stay on USD analytics?

GBP, CHF and EUR are currently baked in a USD context because the library carries USD and GBP configs. It is recorded and stamped, but it is a live analytical caveat. Either accept it explicitly and say so on screen, or get native configs and drop the substitution.

Decision 3

What cadence does the SAA extract actually have?

The rebake schedule should follow the supplying database, not a guess. Quarterly is assumed here. If it is monthly, the bake wants automating rather than running by hand.

Decision 4

Who is a PMG admin?

Sleeve data has no release gate — the admin list is the control. It currently holds one developer. Deciding this list is deciding who can change what advisers see, with no review step.

Decision 5

Is the fee card blocking?

Every fee on screen is a placeholder, and the tool says so honestly at every layer. Whether that blocks any client-facing use is a business call, and it should be made explicitly rather than discovered.

Decision 6

Where does the class-D review sit?

Floors, tilt, premium, hedge ratios and the context window need an annual owner. Investment committee, product governance, or you — but named, and calendared.
