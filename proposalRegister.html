Proposal Tool · design proposal · revision 2

A permanent register of every proposal delivered

Persist every completed proposal so three things can always be read back: the strategic allocation proposed, the implemented model it became once sleeves were attached, and the workbook exactly as it was delivered, downloadable again on demand. Analytics and pricing are not recorded as fields — but they are inside the file, and this revision is explicit about what that means.

Revised 3 September 2026 Change the workbook is kept, and re-downloadable Status built (D69) — record-first, plan name as a column, workbook kept

Keeping the file draws the line somewhere new — worth reading first

The workbook is not a neutral container. Its risk_dashboard holds 34 rows of return, volatility, stress and VaR; its assumptions sheet holds 26 rows of per-asset estimates; and its Implementation sheet prints, in plain text on rows 2 to 5:

Fee Schedule        CASP
Fee Level           PMG Target
Account Size Tier   T4 ($50m – $100m)
Fee Card            0.0-placeholder · placeholder

So the analytics and the pricing are retained once the file is kept. What the earlier instruction still achieves — and it is a real and common distinction — is that they are not structured, not queryable and not indexed. The register can hand you the document a client received; it cannot tell you which proposals quoted above 60 bp, or what the average Sharpe was last quarter, and it never will.

The line is now: queryable data versus the delivered artefact. That is the sentence to agree or reject, because everything below follows from it.

One inconsistency to resolve deliberately

The register would refuse a feeSchedule column while storing a file whose second row reads Fee Schedule: CASP. The information is retained either way; the only question is whether it can be searched.

I would keep the plan name as a column — schedule and level, no rates, no tier — so an admin can answer "which proposals went out on RDR?" without opening 400 files. If the intent is that pricing must not be queryable at all, then the column stays out and that is coherent too; but it should be the intent, not an accident of two instructions arriving in sequence. This is question 2 in §9.

The artefact · opaque

The workbook

17 KB of xlsx, stored byte for byte with a SHA-256 beside it. Never parsed, never indexed, handed back whole.

It is already a zip — compressing it again saves 5%, so it goes in as it comes out.

The hash is what makes "this is the file they received" a checkable claim rather than an assurance.

Store the resolved names in the JSON anyway

Even with the file kept, the two pictures should carry product names, tickers and vehicles inline rather than bare ids. A blob answers "show me the document"; it cannot answer "which proposals used this product" without opening every one. The pictures are what make the register queryable, and they are only worth having if they stand alone.

3Why the sleeve revision still matters

A scenario stores sleeves as names — {"Public Equity": "Passive"} — resolved against a database admins edit daily. Recording (sleeveId, revision) makes the implemented picture immutable and makes drift visible: the register can show a proposal used r7 while the library is now at r9. Possible only because D65 made revisions permanent, and it costs one join.

The file does not replace this. A workbook shows what the sleeve held; the revision says which version it was, which is the thing you need to compare against today without diffing spreadsheets.

4What the register can and cannot answer

Three tiers now, because the file changes the middle one.

By query

  • What allocation went to this PWA, and when
  • Which products implemented it, at what weights
  • Which sleeve version, and has it moved since
  • Who produced it, who started it
  • Volumes by person, PWA, currency, book, period
  • Whether the tilt or premium was applied

By opening the file

  • The return, volatility and Sharpe shown
  • The stress and VaR figures
  • The fees quoted, and on which schedule
  • The per-asset estimates behind it all
  • Exactly what the client saw

One proposal at a time, by a person, not a query.

Not at all

  • Aggregates over anything in the file — average fee, fee distribution, risk profile of the book
  • "Find every proposal quoting over 60 bp"
  • Whether the analytics have been rebaked under a proposal since

These need columns, and columns are what was excluded.

A 17 KB blob belongs in the database, not beside it. SQLite reads blobs of this size faster than the filesystem does, and keeping them in the row makes the write atomic — a proposal cannot end up recorded with its file missing, or filed with no record. One file to back up rather than a table and a directory that can drift apart.

6Downloading one, measured

You asked what this costs at scale, so I built the register at 100, 1,000 and 10,000 proposals with real 17 KB workbooks in it and timed a single download. The short answer is that the database is not the part you will wait for.

Register sizeFile on diskDownload one, warmA 50-row pageChange
100 proposals2.9 MB0.02 ms0.14 ms—
1,000 proposals28.8 MB0.02 ms0.14 msnone
10,000 proposals287.4 MB0.03 ms0.15 msnone

Flat, because the work does not grow. Fetching a workbook is a primary-key lookup in a B-tree — thirteen comparisons at ten thousand rows against seven at a hundred — followed by reading about five 4 KB pages. A hundredfold more proposals changes neither number meaningfully.

The honest case: nothing cached

ConditionFetch one workbookWhat is included
Warm — the service has been running0.03 msThe index lookup and five page reads
Cold connection, fresh process1.1 msOpening the database as well
Cold, OS page cache flushed2.5 msEverything, from an unread 287 MB file

Two and a half milliseconds is the worst case I could construct, on a 287 MB register with the operating system's cache deliberately evicted. In practice the service is warm and it is thirty microseconds.

What you will actually wait for

2.5 msthe database, worst case
5.3 msan HTTP round trip through the proxy
~8 msa download from the register, end to end
97 msgenerating the same file fresh, today

Serving a stored workbook is about twelve times faster than making one

The export endpoint takes ~97 ms today, almost all of it building the workbook. Handing back a stored one skips that entirely: the request is dominated by the Flask-to-FastAPI hop, which is 5 ms whatever the response contains. A download from the register will feel instant, and will keep feeling instant.

The two ways to get this wrong

Both are avoidable, and both are worth writing down because they are the only ways the numbers above stop being true.

Mistake one

SELECT * on the list

A 50-row page costs 0.14 ms with named columns and 0.67 ms with SELECT *, because the blobs get dragged through for rows nobody asked to download. Five times slower, still fast — but the multiplier grows with the page, and it is free to avoid.

The panel names its columns. The blob is fetched only when someone clicks download.

Mistake two

No indexes on the filters

This, not the blob, is the real cost. Unindexed, grouping by person over 10,000 proposals takes 16 ms and filtering by PWA and date 6.2 ms — both full scans.

Five composite indexes, built in 132 ms and costing no measurable space against the blobs, take those to 0.56 ms and 0.13 ms. Twenty-nine and forty-eight times faster.

And a layout question that turned out not to matter

I tested the workbook inline in proposals against a separate proposalWorkbooks table. With named columns the page query is 0.14 ms either way and the download is identical. The split only helps the query you should not be running.

So the blob stays inline, which is the simpler schema and makes the write atomic — a proposal cannot be recorded with its file missing, or filed with no record.

7The store and the schema

A second SQLite database the tool owns, on the sleeveRepo pattern — schema version in meta, migration on connect, an environment override for the host — behind a five-function module so the storage can move to a host table later without touching the endpoint or the panel.

Reading a list must not drag the blobs along. The panel's table selects named columns and never SELECT *; the file is fetched only when someone asks to download one. Worth stating because it is the one way this schema could be made slow.

The write path

content = port.build_export(basis, mandate, results, implementation)
+ register.record(scenarioId, user, basis, mandate, results,
+                 implementation, model, content, filename)
return Response(content=content, media_type=_XLSX, headers=...)

Two supporting changes come with it, both small:

  • scenarioStore.createScenario gains a createdBy. The kerberos is already at the endpoint; it is simply never written down.
  • The implemented model is built inside the writer today. The register needs that model, not a recomputation of it, so buildImplementationRows should be called once in the endpoint and passed to both — otherwise the record is of a model built again, which is nearly the same thing and not the same thing.

The decision that has not changed: does a failed write block the download?

I still recommend yes — record first, deliver second. "Every single proposal is persisted" and "the download always works" cannot both be absolute, and a register with silent holes is worse than none because it will be trusted. The write is a single insert of ~30 KB into a local file, inside a request that already takes 130 ms.

Keeping the file strengthens this rather than weakening it: the whole point of storing the artefact is to be able to say this is what was sent, and that claim is worth nothing if the row is sometimes missing. The case against is unchanged — a PWA in front of a client should perhaps never be blocked by bookkeeping — and if it wins, the write moves to a background task with an alert, and the register is best-effort, said out loud.

9What I need from you

1
Does a failed write block the download?

Still the only decision that cannot be deferred. My recommendation is that it blocks — the point of keeping the artefact is to say "this is what was sent", and that is worth nothing if rows are sometimes missing. The case against is a PWA sitting with a client.

2
Does the pricing plan get a column?

Sharper now that the file is kept: the workbook prints Fee Schedule: CASP on row 2, so the information is retained either way. A column — schedule and level, no rates — makes it searchable. Leaving it out means pricing is deliberately un-queryable, which is coherent, but should be chosen rather than inherited.

3
Is "not saved as fields, but present in the file" the line you want?

It is a normal and defensible one — the artefact is evidence, the columns are data. But it does mean the analytics and fee quotes are retained forever, and anyone assuming otherwise from the earlier instruction should be corrected now rather than later.

4
SQLite here, or a table in the host?

The seam makes it reversible and need not block the build. Note the blob makes this slightly weightier — 1.5 GB at fifty thousand proposals — so if the host is the destination, its DBAs should hear the number early.

5
Who can read it, and is "forever" literal?

Admin-only is assumed. There is no client name anywhere in the tool — the mandate is two amounts and a PWA — but an adviser's name against mandate sizes over time is a picture of their book, and the workbooks now carry fee quotes alongside it.
